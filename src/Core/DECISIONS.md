# Ядро RAS v. 2.0 — решения и идеи

Что решили по ядру (и загрузчику), почему так и что отвергли. Здесь же планы и идеи. Решения ядра касаются всех модулей —
перед изменением ядра прочитать этот файл. Общие правила — `PRINCIPLES.md`, сборка и выпуск — `CLAUDE.md` в корне.
Решения до 05.10.2026 — в редакциях `PRINCIPLES.md` и в истории git.

Как вести файл — как `DECISIONS.md` модулей: новое решение сверху своего раздела (дата, решение, почему, что отвергли,
состояние); решения не удаляются — передумали, новая запись со ссылкой на прежнюю; идея без решения — в «Идеи».

## Запланировано

### Продукт для любой компании: один пакет, лицензия, своё название (13.10.2026)

**Повод.** Разработчик: плагин может понадобиться другим компаниям — целиком или частью, вплоть до функций под них; учесть варианты и не потерять в качестве. Ориентир — ModPlus: ставится общий пакет, функция без лицензии не работает. Заменяет «профиль поставки» (сборку под каждую компанию) из решения «Поставка другой компании» ниже; карта привязок к RAS оттуда остаётся в силе.

**Решение (план на будущее; код — когда разработчик скажет начинать).**
- **Своё название у продукта, без «RAS»** — с названием «RAS» плагин выглядит как плагин компании RAS. RAS — **первый заказчик**. Название — не выбрано; варианты (проверить: поиск в интернете и среди плагинов Revit, домен, товарный знак): Отвес, Нивелир, Ревизор, Трасса, Ватерпас, Каркас, Ориентир, Модулор («Контур» — нет: крупная компания).
- **Один общий пакет для всех** — одна сборка: что проверено у себя, то и уезжает к другим; сборки не расходятся. Вкладка, «О плагине», установщик — с названием продукта, одинаковые у всех.
- **Лицензия — подписанный файл** на сервере компании в `Config` (как `modules.txt`): компания, домен Windows, модули (при нужде — части модулей), срок; подписан закрытым ключом разработчика. Проверка — в ядре и в каждом модуле. Без лицензии кнопка видна, с замком, по нажатию — объяснение; в «О плагине» — что открыто, до какого числа. Пробный период — лицензия с коротким сроком. У RAS — тоже лицензия: все модули, без срока. Выдача — маленькая программа у разработчика. Сервер лицензий в интернете — только если начнутся широкие продажи.
- **Функция только для одной компании** — отдельный модуль по правилам PRINCIPLES.md, отдельным дополнительным пакетом только ей (в общий пакет не кладётся).
- **Адрес сервера и папок — при установке** (`install.cmd`), а не в коде (тогда и загрузчик один на всех; одна переустановка загрузчика — вместе с другим его обновлением).
- **Обновления** — пакетом выпуска на сервер компании (каналы «тест» / «все»).
- **Защита кода** — запутывание (Obfuscar; карта переименований — только у нас) перед первой поставкой наружу: не запутывать то, что Revit и загрузчик ищут по имени, свойства для привязок WPF, поля JSON, сайт (Blazor). Пробу не делаем сейчас (решение разработчика). Подпись сертификатом — по желанию.
- **Просьбы компании — в одну из четырёх корзин:** улучшение для всех → в продукт; их привычки → настройки; только их функция → отдельный модуль; их окружение → настройки установки. Никогда — условий в коде «если компания такая-то». По каждой компании — журнал решений (что просили, куда отнесли, почему), список изменений в каждом пакете, их тестовая группа и канал «тест».

**Настройки, зависящие от компании (обсуждено с разработчиком).** Общую систему настроек компании (кнопка «Настройки» с разделом «компания», права BIM-менеджера) **не делаем**: от привычек компании зависят только два модуля, а будущие инструменты — транзакции в Revit с простыми локальными настройками («какой типоразмер марки ставить»).
- **RAS-Clash Analysis** — свои настройки **на сайте** (раздел «Настройки»): коды разделов в именах моделей, слова критичности и блоков в названиях папок, знак заказчика; значения RAS по умолчанию (план — в `DECISIONS.md` модуля).
- **RAS-Model History** — почти ничего не зависит от компании.
- **Инструменты Revit — без зашитых семейств, типоразмеров и параметров компании** (PRINCIPLES.md, раздел 6, ред. 10): выбор — у человека из того, что есть в проекте, или найденный инструментом и предложенный; общие параметры — по GUID из настроек; настройка проекта хранится **в модели** (Extensible Storage), личные удобства — у человека. Особенно — при переносе функций прежнего RasPlugin (гильзы, муфты, КЖ — почти наверняка завязаны на семейства и параметры RAS).
- **Ядро** — общая «настройка инструмента в модели» для модулей — когда появится первый такой инструмент.

**Обновления у другой компании (план, 14.10.2026).** Сейчас вся система держится на одном адресе, вшитом в загрузчик (`RasPaths.ServerRoot`: `Releases`, `Config`, `Setup`, `Data`). Для другой компании:
1. **Адрес сервера — при установке:** `install.cmd` получает адрес их папки (параметром или вопросом) и записывает рядом с загрузчиком; загрузчик берёт его оттуда, а без него — вшитый адрес RAS (у RAS ничего не ломается). Изменение загрузчика — одна переустановка у тех, у кого он стоит.
2. **«Подготовить сервер»** — скрипт для их администратора: та же структура (`Releases`, `Config`, `Setup`, `Data`), первая сборка и установка.
3. **Пакет выпуска вместо `publish.cmd`** (доступа к их серверу у нас нет): у нас — «собрать пакет» (архив со сборкой и «что нового»); у них — `import.cmd пакет.zip test` кладёт сборку в их канал «тест»; дальше те же `promote.cmd`, `rollback.cmd`, `status.cmd` — по их серверу.
4. **Сайт коллизий** — обновление из пакета, без сборки из исходников (сейчас `site.cmd` собирает из исходного кода).
5. Позже, если компаний станет много, — свой сервер обновлений в интернете, как у ModPlus.
Компания получает сборки, пакеты и скрипты установки и выпуска (`.cmd` / `.ps1` — текст, их видно, но в них нет логики плагина); исходного кода плагина — нет. Делать вместе с переименованием продукта: загрузчик меняется один раз ради всего сразу.

**Раскладка ленты у другой компании (план, 14.10.2026).** Сейчас ядро берёт только вшитый `ribbon.txt` (отделы RAS: BIM, КЖ, ОВ/ВК, АР). При одном пакете для всех вшитая раскладка у всех одна, а пересобрать её под себя компания не может (кода нет). Поэтому: ядро сначала ищет `ribbon.txt` в `Config` на сервере компании, нет — берёт вшитый; администратор компании настраивает его один раз. Правка ядра (не загрузчика) — к этапу переименования.

**Порядок работ, когда начнём:** 1) название; 2) переименование (вкладка, «О плагине», модули, сайт, установщик, папки на компьютере и сервере, имена сборок) — самое дешёвое время сейчас, пока плагин не в работе; 3) адрес сервера — при установке; 4) настройки сайта коллизий; 5) лицензия; 6) запутывание — перед первой поставкой наружу.

**Отвергли.** Сборка под каждую компанию по профилю поставки — своя вкладка, сборка, проверки на каждую. Вторая, параллельная версия для распространения с ручным переносом изменений — каждое изменение дважды, версии расходятся. Название «RAS» для всех. Выключать лишние модули через `modules.txt` вместо лицензии. Общая система настроек компании в Revit — не нужна при двух зависимых модулях.

**Состояние:** запланировано; название не выбрано.

### Поставка другой компании (13.10.2026) — «профиль поставки» заменён решением «Продукт для любой компании» выше; карта привязок к RAS — в силе

**Повод.** Разработчик: плагин может понадобиться другой компании, и не целиком — одним модулем; разбираться, возможно, придётся срочно. Решено подготовиться заранее: записать план и правило (PRINCIPLES.md, ред. 9), код пока не трогать.

**Решение.**
- **Один код — разные поставки.** Не копия проекта (копии расходятся, исправления — дважды), а **профиль поставки** на каждую компанию — файл в репозитории, например `Поставки\<Компания>.txt`:
  ```
  Модули = ModelHistory
  Сервер = \\srv-company\Plugins\RevitTools
  Вкладка = Company Tools
  Папка на компьютере = CompanyTools
  ```
  У RAS — такой же профиль (нынешние значения).
- **Сборка по профилю** (`publish.cmd -Поставка <Компания>` или отдельная команда): в комплект физически попадают только загрузчик, ядро и модули профиля — чужие модули не уезжают, а не «выключены».
- **Обновления — пакетом выпуска:** архив со сборкой и скриптом; администратор компании выкладывает его в свои каналы «тест» и «все» (как `publish.cmd` / `promote.cmd` у нас). Доступ в их сеть не нужен.
- **Свой загрузчик и установщик у компании:** адрес сервера и имена папок вшиты в загрузчик (`RasPaths`), поэтому у компании — свой загрузчик со своими значениями и свой `install.cmd`. Свой `AddInId` в манифесте — чтобы у человека, у которого стоят оба плагина, они не конфликтовали.
- **Версия договора ядра с модулями:** модуль объявляет, с какой версией ядра работает, — чтобы не поставить новый модуль на старое ядро.
- **Сейчас код не меняем:** правка `RasPaths` меняет загрузчик → всем пользователям RAS пришлось бы заново запускать `install.cmd` без пользы для них. Выносим всё в профиль, когда появится реальная компания.

2. Вынести из кода в профиль: `RasPaths` (сервер, папки), `Host.TabName`, «О плагине», манифест, установщик, `Release.ps1`. Сборка RAS после этого должна получаться **побайтно прежней** (загрузчик RAS не меняется — людям не переустанавливать).
3. В нужном компании модуле — привычки RAS в настройки (карта выше).
4. Сборка и пакет по профилю; проверка на чистом компьютере: установка, запуск, выпуск в их «тест», обновление, откат.
5. Инструкция для их администратора (установка, выпуск пакета, откат, где журналы) и для пользователей — на основе `README.md` и `Как выпускать.md`.
6. Поддержка: как они присылают журналы ошибок (`%LocalAppData%\<папка>\Logs`), кто отвечает.

**Отвергли.** Отдельная копия проекта для компании — расходится с основной. Выключать лишние модули у компании через `Config\modules.txt` — их код всё равно уезжает. Переименовывать сборки и пространства имён `RASv2` — дорого, пользы нет.

**Состояние:** запланировано; сделано — правило в PRINCIPLES.md (ред. 9) и эта карта. Код — когда появится реальная компания.

### Выключение модулей (06.10.2026)

**Решение.** Модули выключает BIM-менеджер централизованно — файлом в `Config` на сервере (например, `Config\modules.txt`), без новой сборки. Нужны все четыре случая:
- аварийный — выключить сломанный модуль у всех, пока готовится исправление;
- выборочный — модуль только определённым людям или отделу (и сначала только тестовой группе — PRINCIPLES.md, раздел 4);
- личный — человек сам убирает ненужное (см. порядок ниже);
- фоновый — модуль работает, а кнопки видны не всем (например, журнал пишется у всех, смотрят руководители).

Глубина выключения — все три варианта:

| Вариант | Что происходит |
|---|---|
| не загружать | сборка модуля не загружается совсем — для модуля, который падает уже при загрузке |
| не запускать | загружен, но не стартует: ни кнопок, ни событий |
| скрыть кнопки | модуль работает в фоне, кнопок нет (у всех или у части людей) |

Правила:
- Срабатывает после перезапуска Revit — так же, как обновления плагина.
- Люди указываются по учётной записи Windows, а не по имени пользователя Revit: его легко подменить.
- Сервер недоступен — работает последняя загруженная копия файла: пропажа сети не должна включать выключенное или выключать всё.
- Ошибки в файле не ломают запуск: строка пропускается, причина — в журнал ошибок.
- «О плагине» показывает у каждого модуля состояние и причину: «работает», «выключен в общих настройках», «выключен вами», «только для тестовой группы», «отключён: ошибка при запуске», «отключён: слишком много ошибок».
- Логика (кому что положено по файлу) — без Revit API, с тестами.

**Порядок.**
1. Централизованное выключение (`Config`) и предохранитель: модуль, который за короткое время много раз падает в обработчиках событий Revit, ядро отключает до перезапуска — иначе он сыплет ошибками на каждое действие и тормозит Revit.
2. Личное выключение — позже, когда модулей станет много; только для необязательных модулей. Обязательные (например, RAS-Model History: если выключить у себя — дыра в журнале команды) лично не выключаются.

**Почему.** PRINCIPLES.md (разделы 4, 7, 10) обещает выключение в общих настройках и выпуск нового модуля сначала тестовой группе, а в ядре есть только автоматическое «упал при запуске — выключен до перезапуска».

**Отвергли.** Выключение на ходу, без перезапуска Revit: каждый модуль должен был бы корректно останавливаться посреди работы, а нужно это редко — сломанный модуль проще выключить до перезапуска или откатить сборку.

**Уточнено 06.10.2026.**
- Первый этап — модуль у всех целиком: `Config\modules.txt`, строка на модуль — `<код модуля> = работает | без кнопок | только тест | выключен | не загружать`. Код модуля — `IModule.Id`, он же окончание имени сборки (`RASv2.<код>.dll`): по нему «не загружать» работает до загрузки сборки. Модуля нет в файле или файла нет — работает. «Только тест» — у тестовой группы и у разработчика (каналы «тест» и «разработка»). Непонятная строка пропускается, модуль работает; причина — в журнал ошибок.
- Файл читается при запуске Revit не дольше 3 с; копия — `%LocalAppData%\RAS_v_2.0\Config`. Сервер ответил, а файла нет — копия удаляется, все модули работают.
- Предохранитель: больше 20 ошибок в обработчиках событий одного модуля за минуту — ядро перестаёт вызывать его обработчики, кнопки модуля становятся недоступны; при закрытии Revit модулю всё равно вызывается `Stop` (дописать несохранённое).
- Обязательные модули (которые нельзя выключить лично) отмечаются в коде модуля, а не в `Config`: обязательность зависит от того, что модуль делает (журнал с дырами бесполезен), — это решение разработчика модуля. Понадобится на втором этапе, вместе с личным выключением.

Файл — `src\Core\modules.txt`, тот же формат; едет в сборке рядом с `ribbon.txt` (`tools\Release.ps1` копирует его в выпуск), ядро читает его из папки сборки (`Host.LoadSwitches`); чтение с сервера с копией (`ServerConfig`) удалено, `Config\modules.txt` больше не читается. ### Раскладка ленты: отделы, подписи, стопки (08.10.2026)

**Решение.** В `src\Core\ribbon.txt` задаётся вся лента: отделы, панели, порядок кнопок, их подписи и размер. Сделано сразу, не дожидаясь модуля другого отдела (решение разработчика).

```
[Плагин]                                  ← панель до первого отдела: видна во всех отделах
Core.About

[[Конструктив]]                           ← отдел
[История модели]                          ← его панель
ModelHistory.Journal подпись="Журнал\nизменений"
(                                         ← стопка: 2–3 маленькие кнопки в одну колонку
ModelHistory.History  подпись="История"
ModelHistory.Settings подпись=""          ← без подписи, одна иконка
)
(                                         ← следующая стопка — следующая колонка
…
)
```

Правила:
- **Отделы** — как в решении от 06.10.2026 ниже, с уточнениями: на выпадающей кнопке (на месте «О плагине») — **ровно название отдела** из `[[…]]`; панели разных отделов — **разные панели Revit** (у панели имя на вкладке уникально; название на ленте — без отдела), поэтому одна панель в двух отделах может быть с разными кнопками, а одна кнопка — стоять в нескольких отделах; отдел без единой оставшейся кнопки в переключатель не попадает; «О плагине» (переключатель) должен стоять на панели до первого отдела — иначе из чужого отдела не вернуться: тогда он ставится туда сам, причина — в журнал ошибок. Отделов — до 10 (команды «отдел 1…10»).
- **Подпись** — `подпись="…"` у любой кнопки, большой и маленькой: своя подпись вместо подписи модуля; `подпись=""` — без подписи (Revit API пустую подпись и невидимые знаки не принимает — «The value cannot be empty»; поэтому подпись остаётся, а показ текста выключается во внутренней ленте Revit: AdWindows, `ShowText = false`; если лента при запуске ещё не готова — повтор в простое, 08.10.2026); `\n` — перенос строки (у большой кнопки), `\"` — кавычка.
- **Размер** — в Revit два: большая (иконка 32, подпись под ней) и маленькая (иконка 16, подпись справа). Маленькие бывают только в стопке по 2–3, поэтому размер задаётся стопкой: внутри `( … )` — маленькие, вне — большие; несколько стопок подряд — несколько скобок. Больше трёх в стопке — первые три в ней, остальные большие; кнопка из стопки пропала (модуль выключен, не работает в этой версии Revit) — стопка сжимается, одна оставшаяся — большая.
- Ошибка в строке ленту не ломает: строка пропускается или применяется как может, причина — в журнал ошибок.
- **«О плагине»** показывает коды всех кнопок и подписи, заданные модулями, и выбранный отдел — чтобы составлять раскладку, не заглядывая в код.

**Почему.** Раскладку должно быть так же просто менять, как размещение по панелям: правкой одного файла. Подписи модулей не всегда подходят панели, а иконки без подписи экономят место. Стопки — явно скобками, а не автоматически по «размер=маленькая»: при автоматической сборке добавление одной кнопки перетасовывало бы соседей по стопкам; скобками в файле видно ровно то, что будет на ленте.

**Отвергли.** `размер=маленькая` с автоматической сборкой стопок (см. «Почему»); одна общая панель Revit на все отделы с прятанием отдельных кнопок — кнопки внутри стопок прятать нельзя без поломки колонок.

**Логика** (разбор файла, стопки, отделы, отдел при запуске) — `RibbonLayout`, без Revit API, с тестами; постройка в Revit — `RibbonBuilder`, команды отделов — `DepartmentCommands`. Выбранный отдел — `%AppData%\RAS_v_2.0\department.txt`.

**Состояние:** сделано; в Revit не проверено.

### Отделы на ленте (06.10.2026) — заменено решением «Раскладка ленты: отделы, подписи, стопки» (08.10.2026) выше

**Решение.** Когда одной вкладки станет мало, кнопки раскладываются по отделам (Конструктив, BIM и т. д.): выпадающая кнопка вместо «О плагине» — внутри «О плагине» и список отделов; выбрал отдел — на вкладке видны только его панели. Размещение по отделам — тем же файлом `ribbon.txt`, одной новой пометкой: `[[Отдел]]` — отдел, панели под ним — его.

```
# панели до первого отдела видны всегда
[Плагин]
Core.About

[[Конструктив]]
[Армирование]
Kj.Partition
[История модели]
ModelHistory.Journal
ModelHistory.History

[[BIM]]
[История модели]
ModelHistory.Journal
ModelHistory.Settings
```

Правила:
- Нет ни одного `[[отдела]]` — всё как сейчас, переключателя нет: нынешний `ribbon.txt` остаётся правильным без правок.
- Отделы есть — «О плагине» становится выпадающей кнопкой («О плагине», разделитель, отделы); выбранный отдел подписан на кнопке («RAS v. 2.0 · Конструктив»).
- Панели до первого отдела видны всегда. Одна панель может быть в нескольких отделах — на ленте она одна, видна в каждом из них.
- Кнопка, которой нет в раскладке, — на панели своего модуля, видна во всех отделах: новый модуль не теряется, и видно, что раскладку пора поправить.
- Выбор отдела запоминается у каждого человека (личные настройки, `%AppData%\RAS_v_2.0`); после перезапуска Revit — его отдел. Пока человек ничего не выбирал — первый отдел в списке.
- Новый отдел — строка в файле, без правки кода.
- Переключение — скрытием панелей (`RibbonPanel.Visible`), не пересозданием ленты.
- Кнопка в выпадающем списке не передаёт команде, какой отдел выбран: в ядре заготовлено N одинаковых команд «отдел 1…N» (≈10) по порядку отделов в файле.
- Логика (разбор отделов, какие панели видны в каком отделе) — в `RibbonLayout`, без Revit API, с тестами.

**Почему.** Модулей станет много, одной вкладки не хватит. Размещение по отделам должно быть таким же простым, как размещение по панелям сейчас, — правка одного файла.

**Как сделано в прежнем плагине** (`D:\Code\RasPlugin\RAS_2026`, `Modules\Common\RibbonSectionState.cs`, `RasAboutRibbon.cs`) — образец идеи, не кода: выпадающая кнопка «RAS — О программе», разделы со своими значками, переключение скрытием панелей. Не подходит нам: отделы зашиты в код (перечисление `ToolSection`, команда на каждый отдел), модули сами записывают свои панели в отдел (у нас модуль не знает, где стоят его кнопки — раскладка ядра), выбор не запоминается (после перезапуска всегда «Общее»).

**Когда делать.** Не сейчас: один модуль с тремя кнопками, переключать нечего, а в ядро заранее ничего не добавляется (PRINCIPLES.md, раздел 5). Делать, когда появится модуль другого отдела (например, первая функция КЖ из прежнего RAS) или панели перестанут помещаться. Переход — одна правка `ribbon.txt`.

**Открыто (решить при реализации).** Значки отделов на выпадающей кнопке — нужны ли и откуда (ресурсы ядра).

**Состояние:** сделано 08.10.2026 (раньше задуманного — решение разработчика), с уточнениями — см. решение от 08.10.2026.

**Решение.** Все иконки плагина — в одном стиле: плоские контурные (тёмно-серый контур, белая заливка, одна главная деталь цветом отдела), сетка 32, линия 2, палитра из 5 цветов (`tools\IconBuilder\СТИЛЬ.md`). Цвет акцента — по отделу модуля: Общее — синий, BIM — фиолетовый, КЖ — оранжевый, ОВ/ВК — бирюзовый, АР — малиновый (`palette.txt`; цвета придуманы — фирменных у RAS нет; пока подходят). RAS-Model History — отдел BIM.

### Установка — простой install.cmd на сервере (06.10.2026)

**Решение.** Пока полноценного установщика нет — папка `Setup` на сервере: `install.cmd` + `install.ps1` и загрузчик для каждой версии Revit. Пользователь при закрытом Revit запускает `install.cmd`: загрузчик и манифест — в `%AppData%\Autodesk\Revit\Addins\<год>` для каждой установленной версии Revit, без прав администратора; прежние отдельные установки RAS-Model History / SpyPlugin убираются. Повторный запуск безопасен: копируется только изменившееся. Выкладывает установку `publish-setup.cmd` — отдельно от выпусков ядра и модулей (PRINCIPLES.md, раздел 2: изменение загрузчика — отдельный выпуск с особой проверкой); он предупреждает, если загрузчик изменился. `build.cmd` ставит загрузчик разработчику тем же `setup\install.ps1` — логика установки одна.
**Почему.** Без установки плагин нельзя раздать коллегам; простой вариант делается быстро и потом заменяется полноценным установщиком без изменений для пользователей (после установки обновления всё равно приходят с сервера).
**Отвергли (пока).** Полноценный установщик (один файл, «Установить / Обновить / Удалить», запись в «Установка и удаление программ») — позже, шаг 7 переезда RAS-Model History.
**Ограничения.** Revit ищется по `C:\Program Files\Autodesk\Revit <год>\Revit.exe` — Revit в другой папке установка не увидит. Удаление — вручную (README).
**Состояние:** сделано; проверено на копии профиля (установка, повторный запуск, уборка прежней установки), у пользователя — не проверено.

### Лента: у модуля свои кнопки, панели — по раскладке ядра (05.10.2026)

**Решение.** Модуль объявляет кнопки (`IModuleContext.AddButton`, код `<Id модуля>.<кнопка>`), ядро ставит их на панели по раскладке `src\Core\ribbon.txt` после запуска всех модулей. Кнопка без раскладки — на панели с названием модуля; кнопок отключённого модуля нет, пустые панели не создаются. PRINCIPLES.md — редакция 3.
**Почему.** Кнопки разных модулей нужно ставить на одну панель по смыслу, а не держать у каждого модуля свою.
**Раскладка — файл в сборке**, а не на сервере: правка проходит через git и канал «тест», а не меняется сразу у всех.
**Формат — простой текст** (`[Панель]` и коды кнопок), а не JSON: в .NET Framework (Revit 2023) нет встроенного разбора JSON, а сторонние библиотеки — решение разработчика; в тексте нет кавычек и запятых, в которых легко ошибиться.
**Отвергли.** Раскладку на сервере (`Config`) и сборка + сервер — два места, где искать, почему кнопка там, где она есть.
**Ограничение.** Перенос кнопки на другую панель сбрасывает у пользователей её горячие клавиши и место на панели быстрого доступа — коды кнопок и раскладку после выпуска меняют обдуманно.
**Состояние:** сделано (`a8cdd3c`).

## Идеи

- Выборочное включение модулей по отделам — группами Windows, если айтишники заведут группы отделов: новый сотрудник отдела получает модуль сам.
- Предохранитель не только для событий, но и для фоновых задач модулей в простое Revit.
