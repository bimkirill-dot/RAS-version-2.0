### Список коллизий — по образцу автора статьи (09.10.2026)

**Почему.** Разработчику по-прежнему было неудобно: «непонятно, за какую дату смотрим, ни фильтрации, ни сортировки». Предложили сделать как журнал RAS-Model History (окно условий, сортировка с заголовками, столбцы правым щелчком) — разработчик попросил не копировать всё, а адаптировать, и показал снимок экрана сервиса автора статьи (Clash Analytics). Взяли его устройство, сохранив три пространства (ленты, боковая панель) и наше («Ждёт проверки», «вернулась», группировка, последний прогон).

**Решение.**
- **Все отборы — одной строкой выпадающих списков** на дополнительной ленте: **«Дата»** (последний прогон — по умолчанию, любой прошлый, все прогоны), «Тип проверки», «Блок», «Раздел», «Уровень», **«Статус»** (по умолчанию — активные и ждущие проверки), поиск, «Сбросить». Вкладки статуса — убраны (статус — список с числами, как у автора).
- **Заголовок «Коллизии (N)»**, рядом — что принёс последний прогон, «Группировка» (нет / по типу проверки / по элементу), **«Excel»** (CSV: «;», UTF-8 с BOM).
- **Столбцы как у автора**: Дата (последний прогон, где была), Проверка (с блоком при «все блоки»), Раздел (метка «АР-ОВ»), Имя (↺ — возвращалась), Расстояние (метка «160 мм»), Оси, Уровень, Статус, Повторы (в скольких прогонах встречалась); сортировка по каждому (⇅). При открытой карточке — без «Раздела», «Осей», «Повторов».
- **Страницы**: «‹ 1 2 3 … 6 ›», 50 / 100 / 200 на странице.
- **Карточка как у автора**: сведения таблицей в два столбца (расстояние, оси, уровень, статус, блок, дата, встречалась, проверка, статус Navisworks, критичность), снимок, «Объект А / Б» (ID с копированием, раздел, «категория → семейство → тип», уровень, файл), кнопки статуса (текущий — «✓»), комментарий, «История», «В отчётах».
- «Отчёт» как поле и «Категория» — убраны из отборов (поиск находит и по категории).

**Отвергли.** Копировать журнал RAS-Model History целиком (окно условий «И / ИЛИ», сортировка в 4 уровня с заголовками, столбцы правым щелчком) — для коллизий избыточно (решение разработчика).

**Состояние:** сделано; проверено в браузере без человека (два прогона: дата, страницы, сортировка, статус, группировка, карточка, Excel).

### Исправлена → ждёт проверки; группы по элементу; последний прогон; свои типы; неполный отчёт (09.10.2026)

Предложено после разбора сделанного, разработчик принял пункты 1, 2, 3, 5, 6, 7 (4 — мост в Revit раньше дашбордов — не сейчас).

**Решение.**
1. **«Исправлена» человеком — «Ждёт проверки»**, подтверждает прогон: нет коллизии в следующем отчёте своей проверки — «Исправлена» (в истории — «Исправление подтверждено»); есть — снова «Активная» и **«вернулась после исправления»** (↺, счётчик у коллизии; так же — у исправленной прогоном, которая появилась снова). Статус «Исправлена» руками не ставится. Ручные «Исправлена» до этого — перенесены в «Ждёт проверки» (шаг 3 базы). Вкладка статуса «Ждут проверки», столбец на главной.
2. **Группировка по элементу** («Группировка: По элементу»): коллизия — в группе того из двух элементов, который чаще встречается в списке; группа из одной — к «остальным»; флажок группы — статус всей группе (`ClashGrouping`, с тестами).
3. **Последний прогон** над списком: «+N новых · N исправлено · ↺ N вернулось» — по последнему отчёту каждой проверки; щелчок — только они (статус — «Все»).
5. **Свои названия типов проверок** в проекте («Проверки» → ✎): для всех проверок с этим названием, во всех блоках и будущих отчётах; название другого типа — объединение. Navisworks не меняется.
6. **Отборы:** «Отчёт» убран, «Категория» — под «Ещё».
7. **Неполный отчёт** — когда в файле меньше коллизий, чем Navisworks насчитал в проверке («всего» в итоге отчёта): выгружены не все статусы. Пропавшие из такого отчёта ничего не меняют (неизвестно, исправлены ли), у отчёта и в итоге загрузки — предупреждение.

**Почему.** 1 — главный показатель качества: «исправил» ≠ «исправлено», а возвраты сейчас терялись. 2 — один воздуховод через десять стен — одно решение. 3 — ответ на «как там с проектом?» за секунды. 5 — опечатки в названиях наборов («Ж Горизонтальные…», «MEP»/«МЕР») плодили типы. 6 — отборов стало много. 7 — главный риск правила «нет в отчёте = исправлена».

**Отвергли.** Предупреждать по «подозрительно меньше коллизий» (порог угадывать) — итог Navisworks в отчёте точнее. Отдельный статус «пропала из отчёта» — лишний статус; при полном отчёте пропавшая — исправлена, как и в Navisworks.

**Состояние:** сделано; проверено тестами и в браузере без человека на прогонах 08.10 / 09.10 (подтверждение, возврат, неполный отчёт, группы, переименование типа), перенос базы 2 → 3.

### Узнавание коллизии при смене номера Navisworks (09.10.2026)

**Решение.** Если номер коллизии в новом отчёте незнакомый, сайт сначала ищет известную коллизию той же проверки с той же парой элементов («файл модели + номер элемента», по последнему появлению) и только потом считает коллизию новой. Узнанная по паре — та же коллизия: статус, комментарии и история сохраняются, ключ «личности» меняется на новый номер, в истории — «Номер Navisworks сменился — узнана по паре элементов». Сначала узнаются все коллизии по своим номерам, по паре — только оставшиеся (пара не «перехватывает» коллизию, которая в этом же отчёте есть со своим номером). Неполная пара (нет номера элемента или файла) — по ней не узнаём.

**Почему.** Номер Navisworks живёт, пока проверку прогоняют в том же файле Navisworks. Пересоздали проверку или собрали новый сводный файл — номера другие, и без этого все старые коллизии стали бы «Исправлена», а те же самые — «новыми»: статусы и комментарии потерялись бы. Как у автора статьи: устойчивая «личность» (ClashIdentity) отдельно от появления в отчёте (ClashOccurrence) — у нас `Clashes` и `Occurrences`.

**Ограничение.** Номер элемента Revit (ElementId) в отчёте — не постоянный идентификатор: при пересоздании элемента он другой — тогда коллизия по-честному новая. Постоянный идентификатор (UniqueId) появится с мостом в Revit.

**Состояние:** сделано; проверено тестами и на копии отчётов S08 (у всех коллизий одной проверки — новые номера: 15 из 15 узнаны, «Допущена» сохранилась).

**Решение.** Новый модуль «RAS-Clash Analysis» (код `ClashAnalysis`, сборка `RASv2.ClashAnalysis.dll`, отдел на ленте и цвет иконок — BIM). Источник — XML-отчёты Navisworks Manage 2023 (Clash Detective). Работают все: координатор, проектировщики, руководители. Revit 2023 и 2026 сразу.

**Этапы** (каждый выпускается и проверяется отдельно):
1. **Просмотр.** Окно в Revit: выбрать папку с отчётами XML → список коллизий (проверка, уровень, категории, модели, статус Navisworks, снимок) с фильтрами и поиском → «Показать»: свой 3D-вид пользователя с обрезкой вокруг обоих элементов и временной изоляцией; элементы связанных моделей — тоже (с учётом положения связи). Пока без общих данных команды.
2. **Работа команды.** Отчёты загружаются в общую папку проекта на сервере (`Data\RAS-Clash Analysis`), у коллизии — свои статусы («Активная / Исправлена / Допущена»), комментарии, назначение отделу или человеку, история действий; сравнение отчётов между датами.
3. **Связь с журналом изменений.** Кто и когда создал коллизию (последняя правка элемента перед отчётом), ответственный — по тому, кто менял элементы, «вероятно, исправлена» — элемент изменён или удалён после отчёта.
4. **Дашборды** для руководителей — отчёт HTML по расписанию (тот же, что задуман для аналитики RAS-Model History): проекты, разделы, уровни, динамика, повторяемость.

**Почему так, а не как в статье** (сервис Clash Analytics, habr.com/ru/articles/1033602):
- ~~Без веб-сервера~~ — заменено решением «Плагин + сайт во внутренней сети» выше. Остаётся: без моста `127.0.0.1`; данные — в общей папке на сервере (как журналы изменений); плагин обновляется нашим загрузчиком.
- **Связь с журналом изменений** (этап 3) — у статьи её нет: видно, кто создал коллизию, и исправление замечается до нового прогона Navisworks.
- **Коллизия узнаётся** по постоянному номеру Navisworks (`clashresult@guid` — сохраняется между прогонами одной проверки), запасной вариант — проверка + пара «файл модели + номер элемента». Постоянный идентификатор элемента Revit (UniqueId) запоминается при первом показе — номер элемента из отчёта бывает нестабилен.
- **Статусы и комментарии** каждый пишет в свои файлы (как журнал изменений) — одновременная работа многих людей с общей папкой безопасна.

**Отвергли.** Веб-сервис (нужен свой сервер и сопровождение); проверку коллизий средствами самого Revit вместо Navisworks (медленно на больших моделях; в компании уже принят Navisworks) — может стать идеей на потом.
