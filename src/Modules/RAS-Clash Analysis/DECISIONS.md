### Проекты — вручную; отборы — как у баз данных (09.10.2026)

**Решение.**
- **Проекты добавляет человек**: указывает папку проекта (название подставляется из имени папки, меняется). «Папку со всеми проектами» убрали (решение разработчика): на сайт попадает только то, что нужно; та же папка дважды — нельзя.
- **Отборы переделаны** (разработчику не понравились три ряда кнопок, списки без подписей, отбор вперемешку с отметками): посмотрели аналоги — Autodesk Construction Cloud (статус — несколько значений сразу, отбор по моделям, группировка по уровню / разделу), Revizto (все отборы одной строкой над списком, «Сбросить»), Navisworks (слева — проверки), таблицы данных (Linear, GitHub, Stripe: у поля — список с флажками и числами, выбранное — на кнопке).
  - слева — **дерево** «критичность → блок → проверка» с числом активных: заменило переключатели критичности, блоков и список «Все проверки»;
  - **статус — вкладками** над списком (как «Открытые / Закрытые»);
  - **строка отборов**: поиск и поля «Уровень», «Категория», «Раздел», «Отчёт» — несколько значений, число у каждого, выбранное на кнопке, ✕ — снять, «Сбросить отборы»;
  - **«Раздел»** — новое поле: из имени модели (AR01 → АР, OV01 → ОВ, VK01 → ВК, KJ01 → КЖ).
- Отбор считается на странице (`ClashFacets`, с тестами): из базы — коллизии выбранного в дереве, дальше поиск, поля, статус.

**Отвергли.** Кнопку «+ Фильтр» с добавлением полей по одному (как в Linear): полей всего четыре — видимые сразу понятнее. Сохранённые наборы отборов — пока не нужны (идея).

**Состояние:** сделано; проверено в браузере без человека; удобство — проверяет разработчик.

### Папки отчётов: проекты, критичность, блоки, даты (09.10.2026)

**Решение.**
- **Структура папок на сервере остаётся** «Проект \ дата \ критичность \ формат \ блок \ отчёт» (решение разработчика: с датами — ничего не перезаписывается). Предлагали «Проект \ Критичность \ Блок» без дат и форматов (сайт сам хранит историю) — отвергнуто.
- **Сайт понимает папки по названиям, в любом порядке** (`ReportPath`): критичность, блок, дата прогона; папки форматов и прочие не важны. Опечатка «Срдняя» (так в сообщении разработчика) — тоже средняя.
- ~~**Проекты сами**~~ — заменено в тот же день решением «Проекты — вручную» ниже: на главной — «папка со всеми проектами», каждая папка внутри неё с отчётами XML — проект с названием папки; название меняется на сайте, связь — по папке. Ручное создание проекта — осталось.
- **Внутри проекта — разделение по критичности и по блокам** (решение разработчика: блоки — тоже разделение, не отбор), у каждого — активные; работа (список, карточка, проверки, отчёты) — внутри выбранного.
- **Проверка = проект + критичность + блок + название**: одна и та же проверка «АР Стены/МЕР Трубы» в S1 и S2 — разные проверки. Без этого отчёт S2 считался бы новым прогоном проверки S1 и все коллизии S1 стали бы «Исправлена» (найдено при обсуждении). «Личность» коллизии уникальна в своей проверке (отчёт, скопированный в другой блок, — свои коллизии).
- **Дата отчёта** без дат обнаружения в XML — из названия папки прогона (время — из файла, для порядка внутри дня).

**Состояние:** сделано; проверено на дереве как на сервере (временная папка) и переносом старой базы; на настоящей папке сервера — проверяет разработчик.

### Узнавание коллизии при смене номера Navisworks (09.10.2026)

**Решение.** Если номер коллизии в новом отчёте незнакомый, сайт сначала ищет известную коллизию той же проверки с той же парой элементов («файл модели + номер элемента», по последнему появлению) и только потом считает коллизию новой. Узнанная по паре — та же коллизия: статус, комментарии и история сохраняются, ключ «личности» меняется на новый номер, в истории — «Номер Navisworks сменился — узнана по паре элементов». Сначала узнаются все коллизии по своим номерам, по паре — только оставшиеся (пара не «перехватывает» коллизию, которая в этом же отчёте есть со своим номером). Неполная пара (нет номера элемента или файла) — по ней не узнаём.

**Почему.** Номер Navisworks живёт, пока проверку прогоняют в том же файле Navisworks. Пересоздали проверку или собрали новый сводный файл — номера другие, и без этого все старые коллизии стали бы «Исправлена», а те же самые — «новыми»: статусы и комментарии потерялись бы. Как у автора статьи: устойчивая «личность» (ClashIdentity) отдельно от появления в отчёте (ClashOccurrence) — у нас `Clashes` и `Occurrences`.

**Ограничение.** Номер элемента Revit (ElementId) в отчёте — не постоянный идентификатор: при пересоздании элемента он другой — тогда коллизия по-честному новая. Постоянный идентификатор (UniqueId) появится с мостом в Revit.

**Состояние:** сделано; проверено тестами и на копии отчётов S08 (у всех коллизий одной проверки — новые номера: 15 из 15 узнаны, «Допущена» сохранилась).

### Сайт: первая версия пилота (09.10.2026)

**Решение** (по ходу работы; разработчик проверяет в браузере):
- **Отчёты — только из папки проекта**, загрузки файла через браузер нет: рядом с отчётом лежит папка снимков, браузер её не передаст. Папка проверяется сама (каждые 10 минут) и по кнопке.
- **Новый отчёт** — файл в папке проекта, которого не было, или файл, изменившийся с последней загрузки (Navisworks перезаписывает отчёт на месте). Сравнение — с последним загруженным вариантом того же файла: прогон может вернуть ровно то, что было два прогона назад.
- **Статусы при загрузке** (`ReportMerge`, с тестами): новая коллизия — статус из Navisworks; у известной статус сайта главнее статуса Navisworks; «Активная», которой нет в новом отчёте своей проверки (или Navisworks пишет «Исправлено»), — «Исправлена» (в истории — «Нет в отчёте от …»); «Исправлена», которая снова в отчёте, — «Активная» («Снова в отчёте от …»); «Допущена» остаётся «Допущена». Отчёт старше последнего по проверке статусы не меняет.
- **Снимки** копируются к сайту при загрузке: в папке отчётов их перезапишет следующий прогон.
- **Сайт работает в своём окне**, запускается `site.cmd` (по желанию — при входе в Windows, `site.cmd autostart`). Служба Windows — при переезде на сервер: для неё нужны права администратора.
- **Свои настройки** — `settings.json` в папке сайта: `appsettings.json` рядом с программой заменяется при обновлении.
- **Автор действий** не записывается (пилот без учётных записей); поле в истории уже есть — заполнится, когда решим, как узнавать людей.

**Почему «нет в отчёте» = «Исправлена».** Так считает и Navisworks при повторном прогоне той же проверки; иначе исправленные коллизии висели бы «Активными», и счётчики на главной врали. **Риск:** если отчёт выгружен не со всеми коллизиями (в настройках отчёта Navisworks выбраны не все статусы), пропущенные станут «Исправлена». Выгружать отчёт со всеми статусами; если это неудобно — обсудить.

**Отложено.** Дашборды (графики по разделам, уровням, динамика) — следующий шаг этапа 1; группировка одинаковых коллизий; удаление проекта и отчёта; служба Windows.

**Удобство (разбор по просьбе разработчика, 09.10.2026).** Главная работа на сайте — пройти коллизии подряд и каждой поставить статус. Поэтому:
- список и карточка рядом, а не переход на страницу коллизии и обратно (при возврате терялись отбор и место в списке);
- ↑ ↓ и «после статуса — к следующей»;
- номер элемента — сразу под статусом, с кнопкой «Копировать номер» (сейчас номер копируют руками в «Выбор по коду»);
- статус-отбор — нажимаемые счётчики вместо отдельных плиток и выпадающего списка; строки в один этаж — на экране втрое больше коллизий;
- смена статуса у многих (больше 10) — с вопросом: «отметить все» и одно нажатие меняли весь проект;
- отбор помнится на время работы во вкладке браузера; координаты Navisworks и прочие подробности — в «Подробнее».
**Отвергли:** отдельную страницу коллизии как основной путь (оставлена ссылкой «отдельно» — для ссылки коллеге); бесконечную прокрутку списка (строки появлялись только после подключения к сайту — пустой экран при медленном соединении) — 300 строк и «Показать ещё».

**Состояние:** сделано (`site.cmd`), проверено без браузера; в браузере — проверяет разработчик.

### Пилот, проекты, этапы — уточнения (08.10.2026)

Уточняет решение «Единая база коллизий» ниже; где расходятся — действует это.

Правило без настроек — `ClashRules.LevelKey`: «05 Этаж» = «5 Этаж», регистр и лишние пробелы тоже не различаются; показывается — как в отчёте. Таблица соответствий («Этаж 1» = «01_Этаж») — по-прежнему не нужна.
- **Этапы:**
  1. **Сайт «как в статье»:** проекты и загрузка отчётов (вручную и из папки проекта), разбор, «личность» коллизии через прогоны, список с фильтрами и группировкой одинаковых, карточка со снимком, статусы «Активная / Исправлена / Допущена», комментарии, история, массовые операции, дашборды по проекту и по компании, сравнение отчётов между датами.

  4. **Связь с журналом изменений.**
  5. **Автоматический прогон Navisworks** по расписанию — без ручного запуска BIM-специалистами.

### Единая база коллизий: сайт + мост в Revit, как в статье (08.10.2026)

Заменяет решения «Плагин + сайт во внутренней сети» и «Модуль коллизий» ниже (они оставлены для истории).

**Цель.** Одна база коллизий на всю компанию — по всем проектам и всем разделам: каждый, кто работает над проектом, видит свои коллизии и управляет ими.

**Решение — устройство как у автора статьи** (Clash Analytics, habr.com/ru/articles/1033602):
- **Главное — сайт во внутренней сети.** Загрузка отчётов Navisworks (вручную или сам забирает новые из папки по расписанию), список и фильтры, карточка коллизии со снимком, статусы, комментарии, история, назначение, дашборды по проекту и по компании. ASP.NET Core на C# (страницы — Blazor), вход по учётной записи Windows — без логинов и паролей; кто что сделал — по учётной записи (в пилоте — без учётных записей, см. «Уточнения» выше).
- **Revit — мост для показа.** Модуль RAS-Clash Analysis в нашем плагине (ставится и обновляется загрузчиком) слушает адрес `127.0.0.1` на компьютере пользователя; кнопки на сайте «Показать в Revit» (обрезка 3D-вида вокруг элементов), «Изолировать» — в открытой модели, в том числе для элементов связей (пара «файл модели + номер элемента», с учётом положения связи). На сайте — индикатор: Revit с мостом запущен или нет.
- **Сайт — единственный, кто пишет в базу**, поэтому база — настоящая: выборки по всем проектам, дашборды, поиск.

**Единая база:** Проект → корпус / секция → разделы и их модели → проверки (пара наборов: «КЖ Вертикальные конструкции ↔ МЕР Воздуховоды») → отчёты (прогоны по датам) → коллизия. Коллизия — «личность», живёт через все прогоны (у неё «появления» в отчётах): статус, ответственный (раздел и человек), комментарии, история «кто, когда, что».

**Статусы** — «Активная», «Исправлена», «Допущена», как у автора. Ставит **любой** (в статье о ролях не сказано — см. «Поправка» выше), в том числе сразу у многих коллизий; от ошибок защищает история: у каждой смены — кто и когда. Статус привязан к «личности» и переходит на появления в новых отчётах — работа не делается дважды. При загрузке отчёта статусы Navisworks подхватываются для новых коллизий.

**Где живут сайт и база:**

| Этап | Сайт и база | Защита данных |
|---|---|---|
| пилот | компьютер разработчика, база одним файлом (SQLite) на его диске | копия базы на файловый сервер автоматически — каждый час и каждую ночь |
| вся компания | сервер, когда айтишники дадут машину | обычные резервные копии сервера |

Переезд — перенести программу и файл базы.

**Наши улучшения к статье** (остаются из прежних решений):
- коллизия узнаётся по постоянному номеру Navisworks (`clashresult@guid`), запасной вариант — проверка + пара «файл модели + номер элемента»; постоянный идентификатор элемента Revit (UniqueId) запоминается мостом при первом показе;
- связь с журналом изменений RAS-Model History: кто и когда создал коллизию, ответственный — по тому, кто менял элементы, «вероятно, исправлена» — до нового прогона;
- ~~приведение уровней и разделов к одному виду — таблицей в общих настройках~~ — не нужно, уровни называются единообразно («Уточнения» выше).

**Этапы** (каждый выпускается и проверяется отдельно; ~~этот список~~ заменён этапами в «Уточнениях» выше):
1. **Сайт:** загрузка отчётов, список с фильтрами, карточка коллизии со снимком, статусы, комментарии, история; первые дашборды.
2. **Мост в Revit:** «Показать в Revit», «Изолировать», индикатор.
