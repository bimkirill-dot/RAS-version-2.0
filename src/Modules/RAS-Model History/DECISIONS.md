Что решили по модулю, почему так и что отвергли. Здесь же идеи и планы на будущее. Перед развитием модуля прочитать этот файл: многое уже обдумано, и причины записаны.

## Запланировано

Порядок — сверху вниз. Шаг 6 переезда (Revit 2023) отложен решением разработчика (06.10.2026); план к нему — ниже (13.10.2026).

### Резервные копии моделей — обсуждение (21.10.2026)

**Мысль разработчика:** раз в день — резервная копия моделей, чтобы удалённые элементы можно было восстановить из неё.

**Договорились (21.10.2026):**
- Копию делает **не Revit специалиста**: у него на минуты зависнет работа, а модель совместной работы одна на всех — копировали бы её все по очереди. Копируется **хранилище на Revit Server раз в сутки, ночью, на одном компьютере**: утилита Revit Server Tool идёт с Revit и делает из модели на сервере файл `.rvt` без открытия Revit (`createLocalRvt`; проверить на одной модели); нужен Revit тех же версий, что модели. Программа без Revit — по расписанию Windows, как сайт коллизий.
- **Только модели, которые за день синхронизировали** — это знает журнал модуля; не менявшиеся не копируются (главная экономия места).
- Хранение — **лесенкой**, как копии базы сайта коллизий (`BackupLadder`): числа — по размерам моделей.
- **Не пересекается с автоматическим прогоном коллизий** (разработчик: «должны быть разными и не пересекаться вообще»): копии моделей — только для восстановления.
- **Показ в копии** («в журнале — „есть в копии от 14.10“, открыть копию и показать элемент») — **не нужен** (разработчик): что и когда удалено, и так видно в журнале, а где лежит копия — понятно по дате.
- **«Вернуть удалённое»** (перенос элементов из копии в модель — без замены хранилища целиком и потери чужой работы; «Отвергли (пока)» в «Хранилище заменено копией») — **после того, как продумаем копии**. Ограничение прежнее: вернувшийся элемент — новый ID, марки и размеры на него — заново.

**Открытые вопросы к разработчику:** сколько моделей и какого размера; адрес Revit Server и версии Revit моделей; где хранить и хватит ли места (у айтишников); какой компьютер ночной (компьютер разработчика держит сайт — не спит ли ночью). Проверить: хранит ли сам Revit Server прежние версии моделей (откат в Revit Server Administrator) — откат заменяет хранилище целиком, своих копий не отменяет.

**Состояние:** обсуждение; до ответов на вопросы — не начинать.

### Revit 2023: свои папки журналов для каждой версии Revit (13.10.2026)

**Повод.** Случай: в модели кто-то удалил элементы, модуля ни у кого не было — узнать, кто удалил, модуль не может (он пишет журнал в момент изменений, задним числом не восстановить; для таких случаев — резервные копии хранилища и журналы Revit). Чтобы в следующий раз было видно, модуль должен стоять у всех — и у тех, кто работает в Revit 2023.

**Пробная сборка всего модуля под 2023** (13.10.2026, во временном файле проекта, в репозиторий не попало): мешают только две вещи — JSON (System.Text.Json нет в .NET Framework: 7 файлов, 12 мест) и событие смены темы (в 2023 нет тёмной темы). Номера элементов, 3D-вид, панель, события синхронизации — собрались.

**Решение (план, согласован с разработчиком).**
- **Данные — отдельно для каждой версии Revit:** подпапка `2023` / `2026` везде, где модуль хранит данные, — на сервере (`Data\RAS-Model History\2026\<модель>`, `Data\RAS-Model History\2023\<модель>`) и на компьютере (`%AppData%\RAS_v_2.0\RAS-Model History\<версия>`, `%LocalAppData%\…\<версия>`: личные настройки, вид панели, неотправленные записи, кэш сведений). Подпапку создаёт модуль при первом запуске модели в этой версии; есть — не создаёт (`Directory.CreateDirectory`: одновременный запуск у двоих безопасен). Права у пользователей есть — папки моделей они уже создают сами.
- Так журналы 2023 и 2026 никогда не пересекаются: ошибка версии для 2023 не испортит журналы 2026, и формат JSON в 2023 не обязан совпадать с 2026 до символа.
- **JSON в 2023** — Newtonsoft.Json из папки Revit 2023 (13.0): ничего не подкладываем, конфликта версий нет. В 2026 — как сейчас (System.Text.Json). Отвергли: подложить System.Text.Json в 2023 (Revit 2023 сам загружает старые зависимости — System.Memory 4.0.1.1 — классическая причина падений); перевести и 2026 на Newtonsoft (трогать работающее без выгоды).
- **Тема в 2023** — панель всегда светлая.
- **Нынешние журналы в корне** `Data\RAS-Model History` (10 моделей, все тестовые — разработчик: «плагин в работу не пошёл, ничего не теряем») модуль больше не читает; не удаляются — разработчик удалит сам.
- **Не риск** (разработчик): модель обновили 2023 → 2026 — история до обновления остаётся в `2023`; сводное (аналитика, «Сотрудник») — по своей версии: смотрят одну модель, а она в одной версии.

**Проверка в Revit (разработчик):** запуск без «не работает в Revit 2023»; создать / изменить / удалить — записи в панели; синхронизация — записи на сервере, видны коллеге; 3D-вид изменений; фильтры, «удалён вместе с»; в 2026 — журналы пишутся в `2026`. Выпуск — сначала канал «тест».

**Состояние:** запланировано — когда разработчик скажет начинать.

### Связь журналов (06.10.2026)

**Решение.** Модель по-прежнему узнаётся по номеру хранилища Revit Server (`ModelIdentity.Key`). Если история модели разделилась, журналы связываются:
- Автоматически: при открытии модуль ищет в общей папке журнал с тем же путём на Revit Server (без имени сервера; путь — в `model.json`) и другим номером. Нашёл — полоса в панели «Найдена прежняя история… [Связать] [Это другая модель]», без всплывающих окон.
- Вручную: меню «⋯» → «Связанные журналы…» — список журналов общей папки (модель, путь, записей, период, авторы), связать / отвязать. С предупреждением «Только для BIM-менеджера».
- Связь хранится на сервере, в папке журнала модели (`links.json`), и общая для всех. Связывание и отвязка пишутся событием в журнал, ничего не удаляется. Панель, 3D-вид и аналитика читают связанные журналы вместе, дубли отсекаются по номеру записи. Логика — без Revit, с тестами.

**Почему.** Хранилища — на Revit Server. Когда удалённое восстанавливают, локальную копию сохраняют вместо хранилища под тем же именем и по тому же пути. У нового хранилища, скорее всего, другой номер (проверить на тестовой модели), и журнал модели начинается в новой папке — прежняя история пропадает из панели.

**Отвергли.**
- Узнавать модель по пути и имени вместо номера. Восстановленная модель тогда сама продолжала бы историю, но ключи всех моделей пришлось бы переносить, а переименование или перенос модели начинали бы историю заново. Связь журналов решает обе задачи без смены ключа.
- Ограничить связывание правами. Кто связывает журналы — договорённость в компании; технически — только предупреждение.

**Сделано (22.10.2026, разработчик: «связь журналов и хранилище заменено можем сделать сейчас, вроде это дёшево»):**
- **Поиск:** при первом чтении журнала модели (в фоне, раз за сеанс) — папки общей папки с тем же именем модели в ключе (одним списком), у них `model.json` → путь; то же место без имени сервера, другой ключ, не связан и не отклонён — полоса в панели «Найдена прежняя история этой модели: журнал «…», период (кто писал)» и [Связать] [Это другая модель]. Логика — `Tracking\JournalLinks` (тесты), файлы — `Storage\JournalLinkStore`.
- **Связь** — `links.json` в папке журнала модели (`linked`, `rejected`: ключ, название, кто, когда), общая для всех; связанные читаются вместе с журналом (и связи связанных — цепочка восстановлений, без кругов, не больше 50) — в панели, 3D-виде и актуализации. Связал / отвязал — событие в журнал («Связан прежний журнал», «Связь журналов убрана», поле `lk`); «Это другая модель» — в `rejected`, без события.
- **Вручную:** «⋯» → «Связанные журналы…» (`UI\JournalLinksWindow`): связанные (отвязать), все журналы общей папки с поиском (связать; путь, кто писал, период — у выбранного), предупреждение «только для BIM-менеджера», подтверждение. Для случая, когда модель переименовали или перенесли — полоса её не найдёт.
- После связывания — проверка «Хранилище заменено копией» по связанному журналу (ниже).

**Состояние:** сделано, ждёт проверки в Revit 2026 на настоящем восстановлении хранилища (разработчик).

### «Хранилище заменено копией» (06.10.2026)

**Решение.** Модуль замечает замену хранилища: последней версии хранилища, которую он помнит, нет в истории модели (`Document.IsValidVersionGUID`), или номер хранилища сменился при том же пути. Тогда — событие в журнал «Хранилище заменено копией: кто, когда». Записи, синхронизированные после момента копии, помечаются «✗ потеряно при восстановлении» (момент копии — по номеру версии хранилища, который модуль пишет при синхронизациях). «Актуализация» должна работать и в этом случае.

**Почему.** При замене хранилища копией пропадает чужая работа, сделанная после момента копии, а журнал продолжает считать её «✓ в хранилище». Сравнение «что изменилось с прошлого раза» при этом молча не срабатывает: Revit не сравнивает версии из разных историй хранилища.

**Версия хранилища — в событии синхронизации (22.10.2026, сделано, до остального):** у событий «Синхронизация» и «Обновление до последней версии» — поле `sv` (`ChangeRecord.StorageVersion`: «VersionGUID:N:NumberOfSaves» после синхронизации). Выпущено раньше самой функции, чтобы момент копии был виден для синхронизаций с этого дня (разработчик: «делай» — до выпуска 22.10.2026). Старые записи — без него; прежние сборки плагина поле пропускают.

**Отвергли (пока).** «Вернуть удалённое из копии» — возвращать из копии только удалённые элементы, а не заменять хранилище целиком (этап 1 — модуль выделяет удалённое в открытой копии по идентификаторам из журнала; этап 2 — переносит сам). Решает потерю чужой работы в корне, но пока не нужно. Ограничения, если вернёмся: вернувшийся элемент — копия с новым ID (марки и размеры на него — заново), арматуру возвращать вместе с основой.

**Сделано (22.10.2026):**
- **Когда проверяется:** версии хранилища, которую модуль помнил (`state.json`), в истории модели нет (`Document.IsValidVersionGUID`) — при открытии, синхронизации, обновлении; и после связывания журнала. Только тогда модуль читает журнал целиком (с прежними и связанными).
- **Что пропало** (`Tracking\StorageReplacement`, тесты): синхронизации журнала с версией хранилища (`sv`, с 22.10.2026), чьих версий в хранилище нет, — после последней, что осталась. **Событие пишется, только если такие есть**: одна незнакомая версия без записей `sv` — не повод (без ложной тревоги). Связали журнал другого хранилища — нужна ещё хоть одна оставшаяся синхронизация (иначе, может, у хранилища просто нет прежней истории).
- **Событие** «Хранилище заменено копией — состояние на ДД.ММ ЧЧ:ММ; пропали синхронизации: N (кто)» (`StorageReplaced`): «rt» — первая пропавшая синхронизация, «sv» — версия, на которой замену заметили: замену с версией из нынешнего хранилища уже записали — второй раз не пишется (заметили несколько человек).
- **Статус** «✗ потеряно при восстановлении» (`SyncStatus.LostOnRestore`): записи «вживую», попавшие в хранилище синхронизацией с «rt» до замены. Из журнала не убирается (видно, чья работа пропала), с моделью не сверяется (актуализация его не трогает); «скрыть ✗» — скрывает. Записи, полученные из хранилища (не «вживую»), не помечаются: их время — когда их увидели, а не когда они попали в хранилище.
- Кто заменил хранилище, модуль не знает — в событии тот, кто заметил.

**Первая проверка (23.10.2026) и поправки.** Разработчик проверил на тестовой модели — события не было: копию сделали после всех синхронизаций (в хранилище ничего не пропало, модуль промолчал верно). По журналу найдено:
- **Как восстанавливают** (разработчик): «находим локальную копию на каком-нибудь компьютере и ей заменяем». Открыть старую локальную копию — ещё не замена (в ней просто нет последних версий), поэтому проверка — **только при открытии свежей локальной копии** (создана не больше 15 минут назад: у нас каждое открытие — новой копией) и **после «Сохранить как»**; из разбора изменений коллег (`ProcessRemote`) она убрана — открытие старой копии давало бы ложную тревогу. Запомненная версия — и без настройки «изменения коллег».
- **Сдвиг записи Revit:** сразу после синхронизации `GetDocumentVersion` даёт ещё прежний номер версии, но уже новое число сохранений; новую версию видно при следующем открытии или обновлении. Поэтому синхронизация «G:N» — это версия «G:N−1», а созданную ею версию правило ищет по числу сохранений N в следующих записях; версия пишется и в событие «Открытие».
- **Конец пропажи** — «ru» (последняя пропавшая синхронизация): синхронизации с новым хранилищем до того, как замену заметили, не помечаются.
- **Запись для разбора** в журнал плагина (`ras.log`, «Storage probe»): номер хранилища, версия, число сохранений, запомненная версия и есть ли она в хранилище, локальная копия и когда создана — при каждом открытии и «Сохранить как». По ней — что делает Revit при замене (номер хранилища, история версий, число сохранений); правило доводится после проверки.

**Вторая проверка (23.10.2026) — ложное событие и поправки.** Событие появилось, когда разработчик открыл сохранённую старую копию, а не когда заменил ею хранилище: копия была создана за 3 минуты до этого и прошла как «свежая» (признак по времени создания файла — ненадёжен); при её открытии модуль ещё и запомнил её старую версию — настоящую замену после этого не заметил. По «Storage probe» и журналу:
- **Номер версии** меняется при обновлении из хранилища (в начале синхронизации), синхронизация пишет тот же номер; **«Сохранить как» в хранилище начинает число сохранений заново с 1**, историю версий сохраняет. Поэтому правило (`StorageReplacement.Judge`) — **по времени**: оставшееся — последняя по времени запись, чья версия есть в хранилище (не позже последней пропавшей); синхронизации после неё — пропали. Число сохранений в правиле не участвует (только в записи для разбора). Тесты — на записях этой проверки.
- **Когда проверяется** — только когда модель сверилась с хранилищем: **синхронизация, обновление** и **«Сохранить как» в хранилище** (путь документа — путь хранилища; это и есть замена — её заметит тот, кто заменяет). При открытии — только запись для разбора. Сверяется **версия, увиденная при прошлой синхронизации или обновлении** (`LocalState`, «observed|ключ»), — открытие старой копии её не трогает.
- Ложное событие в журнале тестовой модели «Тест_1» остаётся (журнал не правится): следующую проверку — на новой тестовой модели.

**Состояние:** сделано, ждёт третьей проверки разработчиком (новая тестовая модель, замена старой локальной копией); было — ждёт второй проверки разработчиком — по шагам, как восстанавливают в работе (старая локальная копия с другого компьютера), — и разбора «Storage probe»; было: ждёт проверки разработчиком: восстановить тестовую модель на Revit Server из копии, как это делают в работе, — посмотреть, меняется ли номер хранилища (полоса «Найдена прежняя история») или остаётся (событие «Хранилище заменено копией»).

### Аналитика для главного конструктора (06.10.2026)

**Решение.** Главный конструктор открывает отчёт и видит жизнь модели за период: кто над какими конструкциями работал, сколько времени, сколько ушло на оформление. Плагин сам сводит записи в работы — «Иванов, 1–5 октября, СЖм-12: ~6 ч, 14 операций, 214 стержней», а не показывает сырые записи.

1. **Марка конструкции — в каждой записи** (текущее значение, не только когда её меняют). Параметр марки свой для каждой категории: таблица «категория → параметры (первый заполненный)» в общих настройках компании; для арматуры без марки — марка основы. Таблицу даст разработчик.
   *Почему:* сейчас марка есть только у созданных (не больше 500 элементов одной операции) и удалённых записей. Правка шага у стержня, созданного до плагина, иначе не относится ни к какой марке. В момент правки плагин и так читает все параметры элемента — брать марку почти бесплатно.
   *Уточнение:* работу считать по тем, кто создавал и правил элементы с маркой, а не по тому, кто её присвоил: марки массово переставляет и проверяющий.
2. **Присутствие.** Отрезки «активен; открытый вид; выделенное и его марка» — новая строка только при смене состояния. В отдельных файлах рядом с журналом: панель их не читает, журнал не засоряется. Объём — десятки строк в день на человека. Снятие — в простое Revit, доли миллисекунды. Сначала на 2–3 людях.
   *Почему:* Revit сообщает об изменении, когда операция закончена; между правками — тишина, и без присутствия её приходится угадывать по перерывам. Это поминутный учёт работы — сотрудников предупредить.
3. **Время работы.** Отрезки работы человека — правки с перерывами меньше порога (~15 мин), уточнённые присутствием. Время между правками — на марку следующей правки. Считаются операции (пакеты), а не элементы: «Копировать 200 стержней» — одно действие. Правки без марки — по группам: «Оформление» (аннотации, виды, листы, спецификации — группа записи `ot`), «Прочее». Это оценка, не табель — так и подписывать в отчёте.
4. **Отчёт** — один файл HTML с интерактивными дашбордами, как в Power BI: фильтры (период, люди, марки, категории), перекрёстный отбор, переход вглубь (марка → элементы → правки), лента «кто над чем по дням», тепловая карта «люди × дни», «горячие» марки. Данные и библиотека графиков вшиты в файл: открывается в браузере без сети, пересылается; в Revit библиотека не загружается.
5. **По расписанию.** Программа без Revit (логика модуля, подключённая исходниками, как в проверках) собирает отчёт каждый день планировщиком Windows на компьютере разработчика: `Reports\<модель>\<дата>.html` и всегда свежий последний. В планировщике — «запускать при первой возможности», иначе при выключенном компьютере отчёт не соберётся. Папка `Reports` — только руководителям: в ней поимённые данные о работе.

**Отвергли.**
- Power BI и подобные системы — отдельный инструмент и лицензии.
- Окно с графиками внутри Revit — сторонние библиотеки графиков в Revit 2023 конфликтуют с другими плагинами, рисовать вручную долго.
- Служба на сервере с дашбордом «в реальном времени» — отдельная программа и компьютер-сервер; можно вернуться позже, отчёт тот же.
- Отдельная сущность «ключ конструкции» — марка в параметре и есть ключ, нужно только писать её в каждую запись.

**Состояние:** запланировано. Ждёт: таблицу «категория → параметр марки».

## Принято и сделано

### Окно «Настройки» без путей к файлам; «Журнал» без открытой модели (20.10.2026)

- **Пути к файлам из окна «Настройки» убраны** (разработчик: «давай эти строки из настроек уберём — просто напиши понятную инструкцию, где что и что делать»). Было внизу окна: личные настройки, общие настройки команды, журнал ошибок — путями. Стало — одна строка простыми словами: «Оформление» и «Панель» — личные; остальное одинаково у всей команды — к BIM-менеджеру; что-то не работает — «О плагине» → «Показать журнал ошибок». Подробно — README.md модуля, «Настройки: где лежат и как поменять».
- **«Журнал» на стартовой странице Revit** (без открытой модели): было — окно «Сбой при выполнении внешней команды» («The requested dockable pane has not been created yet»): закреплённую панель Revit 2026 создаёт вместе с первой открытой моделью. Стало — сообщение «Откройте модель — панель журнала появится вместе с ней» (`DockablePane.PaneExists`); то же — у «Закрепить» из окна журнала.

### Отсоединённые модели, сведения об удалённых, «удалён вместе с», таблица (08.10.2026)

**Решение.**
- Отсоединённые модели журнал не ведёт (ни записей, ни событий, ни снимков) — надпись в журнале; «Сохранить как» хранилищем или файлом — событие «Хранилище создано из отсоединённой копии» и журнал с этого момента.
- Удалённое сразу после открытия — не «нет сведений»: выделенное и всё, что от него зависит, запоминается в момент выделения; сведения об элементах хранятся между сеансами; если всё же неизвестно — сведения из прежних записей журнала об этом элементе.
- «Удалён вместе с: …» — у элементов, которые Revit удалил вместе с тем, от чего они зависели; ссылка ведёт к строке удаления родителя.
- «Модель запомнена: N %» — одно число в левом нижнем углу журнала.
- Столбцы параметров — несколько, правым щелчком по заголовку, запоминаются; ненужные столбцы скрываются там же.
- Таблица всегда во всю ширину.
- Копии со штампом даты и времени: несинхронизированное из прежних копий — «✗ не попало в хранилище».

**Почему.** Правки отсоединённой копии попадали в журнал основной модели (отсоединённая копия помнит хранилище) — неправда в общей истории, которую не убирает и актуализация («только в локальной копии»). «Нет сведений» появлялось при удалении сразу после первого открытия: модуль запоминал только первый выделенный элемент, а зависимые (марки, размеры) не запоминал вовсе. Политика компании — каждое открытие новой копией со штампом.

**Отвергли.** Вести журнал отсоединённых копий отдельно — их правки не нужны (решение разработчика). Ручное «убрать сеанс из журнала» — пока не нужно: после исправления отсоединённые сеансы в журнал не попадают (см. «Идеи»).

**Состояние:** сделано; в Revit не проверено.

### Журнал открывается в отдельном окне (05.10.2026)

**Решение.** «Журнал изменений» открывает обычное окно, как «Настройки»: растягивается, разворачивается на весь экран, переносится на другой монитор, запоминает место. Закрепить журнал в панели Revit — кнопкой в окне, выбор запоминается у каждого (`UiState.OpenInWindow`, по умолчанию — окно).
**Почему.** У стыкуемой панели Revit нет «Развернуть» — это ограничение Revit API, не модуля. Окно держится поверх Revit, поэтому панель оставлена по желанию.
**Отвергли.** Только кнопка «в окно» при панели по умолчанию — неудобно: каждый раз лишнее действие.
**Состояние:** сделано (`ff8217f`, `c7e87ff`). **Уточнено 23.10.2026:** закрепление в панели Revit убрано — журнал всегда в окне (разработчик: «надо, чтобы сразу было отдельное окно, мы же договаривались»: кнопка «закрепить», нажатая когда-то, дала узкую панель без «Развернуть»). Сохранённое «в панели» (`UiState.OpenInWindow = false`) не действует; если Revit сам покажет панель с прошлого сеанса, в ней — кнопка «в окно».

### «Сотрудник» — учётная запись Windows в записях (05.10.2026)

**Решение.** Каждая запись несёт учётную запись Windows (`wa`, «ДОМЕН\логин») и полное имя из каталога компании (`fn`) того, кто записал. В подробностях записи — строка «Сотрудник». Для записей из синхронизации сотрудник автора ищется по его собственным записям (`EmployeeIndex`).
**Почему.** «Автор» — имя пользователя Revit: его задаёт сам человек, оно бывает чужим, и по нему долго искать сотрудника. Учётную запись Windows не подменить без чужого пароля.
**Отвергли.**
- IP-адрес: раздаётся автоматически и меняется, при VPN — общий; имя компьютера айтишникам полезнее.
- Сотрудника в столбце «Автор» и предупреждение, когда под одним именем Revit работают разные учётные записи: учётная запись и так видна в подробностях.
**Ограничение.** У записей из синхронизации сотрудник определяется по имени Revit — там подмена возможна.
**Состояние:** сделано (`f813649`).

### Журналы — одна папка на сервере (05.10.2026)

**Решение.** Журналы пишутся и читаются только в `Data\RAS-Model History` на сервере RAS v. 2.0. Прежняя папка отдельного плагина не читается; на сервере она оставлена как есть.
**Почему.** В прежней папке была только проверочная история (события открытия и закрытия одной модели). Папка журналов задаётся ядром, не настройками: если её можно поменять в настройках, одного неверного файла хватит, чтобы история команды разделилась.
**Отвергли.** Читать обе папки до шага 7 — лишняя сложность при пустой прежней папке.
**Состояние:** сделано (`e646c64`, `9708cc7`).

## Идеи

- **Убрать из журнала сеанс или выбранные записи вручную** (для BIM-менеджера): правый щелчок → «Убрать весь сеанс…» / «Убрать выбранные…» → список, причина, предупреждение, если среди них есть «✓ в хранилище», → событие «убрано вручную» (как актуализация, обратимо, файлы журнала не правятся). В подробностях записи — строка «Сеанс: открыт…, закрыт…, кто, компьютер, записей». Понадобится для мусора, попавшего не из-за отсоединённых копий.
- **После замены хранилища копией** — сравнить модель с последним известным состоянием (кэш снимков) и записать разницу: «при замене вернулись 14 стен», «пропали правки Иванова».
- Сотрудник в столбце «Автор» вместо имени Revit (имя Revit — в подробностях).
- Предупреждение, когда под одним именем Revit работают разные учётные записи Windows.
- Отчёт: недельная сводка по понедельникам; служба на сервере с дашбордом в реальном времени.
- Журнал после перезапуска Revit открывается в окне сам, если его оставили открытым.
