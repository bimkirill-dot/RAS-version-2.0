# RAS v. 2.0 — принципы устройства и разработки

Документ для разработчика и ИИ-ассистентов, которые пишут и сопровождают плагин компании «RAS v. 2.0» для Revit. Здесь собраны принципы: как устроен плагин, по каким правилам пишется код, как выпускаются версии и как работать с проектом. Подробности конкретного модуля описаны в его `MODULE.md`, решения по модулю и идеи — в его `DECISIONS.md` (по ядру — `src\Core\DECISIONS.md`), команды сборки и окружение — в `CLAUDE.md`.

Прочитайте документ целиком до начала работы. Если задача требует отступить от какого-то принципа, остановитесь и спросите разработчика.

## 1. Главные принципы

1. **Один плагин, много модулей.** Каждая функция компании — модуль внутри одного плагина. Модули не знают друг о друге и не зависят друг от друга.
2. **Общее — в ядре, своё — в модуле.** То, что нужно всем (лента, события Revit, журнал ошибок, настройки, тема окон), существует только в ядре. В модуле — только его функция.
3. **Ошибка модуля остаётся в модуле.** Она не роняет Revit и не мешает другим модулям.
4. **Обновление без переустановки.** Новая версия выкладывается на сервер; пользователю достаточно перезапустить Revit.
5. **Данные пользователей неприкосновенны.** Форматы меняются только с обратной совместимостью, переносы — только вместе со старыми данными. Ничего не теряется.
6. **Логика отдельно от Revit и окон** — и проверяется тестами до выпуска.
7. **Один стиль для пользователя.** Все модули выглядят и говорят одинаково, по-русски.
8. **Документация — часть работы.** Изменилось поведение — описание обновляется в том же изменении.

## 2. Из чего состоит плагин

### Загрузчик

- Маленькая сборка, которую Revit загружает по манифесту `.addin`. Единственная часть, которую на компьютер ставит установщик.
- При запуске Revit загрузчик определяет канал пользователя, узнаёт на сервере текущую сборку этого канала, при необходимости копирует её в локальную папку и запускает ядро из локальной копии.
- Своей логики не содержит и не зависит от ядра и модулей: связь с ядром — одна точка входа.
- Меняется очень редко. Ошибка в загрузчике ломает плагин у всех и исправляется только переустановкой, поэтому каждое его изменение — отдельный выпуск с особой проверкой.

### Ядро

- Общая часть для всех модулей: регистрация и запуск модулей, вкладка и панели ленты, раскладка кнопок модулей по панелям, подписка на события Revit и раздача их модулям, очередь фоновой работы в простое Revit, вызов Revit API из окон, именование транзакций, журнал ошибок, настройки (общие и личные), пути к данным, совместимость версий Revit, тема и общие элементы интерфейса, окно «О плагине», уведомление об обновлении.
- Ядро не знает, что делают модули.

### Модули

- Модуль — одна функция компании: свой проект (сборка), своя папка в исходниках, свой `MODULE.md`.
- Всё общее модуль получает от ядра и не дублирует.

### Установщик

- Ставит загрузчик и манифест в профиль пользователя, без прав администратора, — для каждой поддерживаемой версии Revit, которая есть на компьютере.
- Модули не ставит: их приносит загрузчик. Повторная установка нужна только при смене загрузчика.
- Убирает прежние установки, которые конфликтуют с плагином.

### Сервер

- Хранит выпущенные сборки, указатели каналов, общие настройки компании и общие данные тех модулей, которым они нужны.
- Права: все читают папку целиком. Записывать всем нужно только в данные модулей, которые собирают общие сведения команды. Выпуски и общие настройки желательно разрешить менять только разработчику: из этой папки код запускается на всех компьютерах.

### Сайт модуля

- У модуля может быть свой сайт во внутренней сети — страницы в браузере и общая база данных — там, где мало Revit и общей папки: одна база на всю компанию, работа людей без Revit, дашборды. Сейчас сайт есть только у RAS-Clash Analysis (единая база коллизий); другим модулям — только по решению разработчика.
- Сайт — часть своего модуля: код, документы и данные — в папках модуля.
- Работает службой Windows на одной машине: сначала — на компьютере разработчика, потом — на сервере компании. Переезд — перенести программу и базу.
- Не часть Revit: загрузчик его не приносит и не обновляет, каналы «тест» и «все» к нему не относятся. Обновляется отдельно (раздел 10).
- В Revit сайт не обращается: в модели действует только модуль. Если странице нужно что-то показать в Revit, она просит модуль на компьютере пользователя («мост»), и мост принимает просьбы только от своего сайта.
- Логика, общая для сайта и модуля в Revit (например, разбор файлов), — один код, без копий.
- Доступ — только из внутренней сети. Пока сайтом пользуется один разработчик, вход не нужен; коллегам сайт открывается, только когда решено, как он узнаёт, кто что сделал.

  Releases\<год Revit>\<сборка>\   выпущенные сборки (не меняются)

Машина сайта модуля (сейчас — компьютер разработчика)

Компьютер пользователя

## 3. Имена

| Что | Правило |
|---|---|
| Название для людей | «RAS v. 2.0»; у модуля — своё короткое название |
| Папки | `RAS_v_2.0` |
| Пространства имён и сборки | `RASv2.Loader`, `RASv2.Core`, `RASv2.<Модуль>`, сайт модуля — `RASv2.<Модуль>.Site`; `<Модуль>` в имени сборки — код модуля (`IModule.Id`) |
| Вкладка ленты | «RAS v. 2.0»; панели — по раскладке ядра (раздел 12) |
| Коды кнопок | `<модуль>.<кнопка>`, например `ModelHistory.Journal` |
| Транзакции Revit | имя с префиксом плагина и модуля; префикс ставит ядро |
| Ключи ресурсов интерфейса | общие — ядра; ключи модуля — с префиксом модуля |

- Имена сборок уникальны и начинаются с `RASv2`. В Revit 2023 все плагины живут в одном пространстве, и одноимённые сборки разных плагинов подменяют друг друга — в том числе сборки прежнего плагина RAS.
- Идентификаторы, от которых зависят сохранённые данные (GUID панелей, AddInId, ключи данных, коды кнопок), после выпуска не меняются.

### Прежний плагин RAS

- Может стоять рядом с RAS v. 2.0. У нового плагина свои сборки, пространство имён, AddInId и вкладка; прежний не трогаем.
- Его функции переходят в RAS v. 2.0 по одной, как модули (порядок — в разделе 4, «Встроить существующий отдельный плагин»).

## 4. Модуль

### Что у модуля своё

- код: проект, папка, пространство имён;
- кнопки на ленте (на какой панели они стоят, решает раскладка ядра);
- общие данные — `Data\<Модуль>` на сервере; данные на компьютере — `%LocalAppData%\RAS_v_2.0\<Модуль>`;
- раздел в общих настройках компании и в личных настройках;
- метка в журнале ошибок;
- `MODULE.md` и `DECISIONS.md`.

### Связь с ядром

- Модуль объявляет себя ядру через один контракт: идентификатор, название, поддерживаемые версии Revit, запуск и остановка.
- При запуске модуль получает от ядра контекст и через него объявляет свои кнопки, подписывается на события Revit, ставит фоновые задачи, получает свои папки, настройки и журнал ошибок, вызывает Revit API из окон.
- То, что нужно нескольким модулям, переносится в ядро (раздел 5). Копировать это или вызывать из соседнего модуля нельзя.

### Чего модулю нельзя

- ссылаться на другой модуль и вызывать его;
- подписываться на события Revit, простой и ленту в обход ядра;
- держать свои копии общего: журнала ошибок, темы, настроек, путей, очереди задач;
- писать в чужие папки и разделы настроек;
- менять модель Revit транзакцией, названной не по правилам ядра;
- показывать окна из обработчиков событий Revit: это блокирует работу. Вместо этого — сообщение в своей панели или уведомление через ядро.

### Новый модуль

1. Описать в `MODULE.md`: зачем он нужен, для кого, что делает, какие данные хранит и где, в каких версиях Revit работает. Завести `DECISIONS.md`: решения, принятые при обсуждении модуля, и идеи.
2. Создать проект по образцу существующего модуля.
3. Зарегистрировать в ядре, при необходимости поставить кнопки на нужные панели в раскладке; в общих настройках включить сначала только для тестовой группы.
4. Логику писать отдельно от Revit и окон, с тестами.
5. Выпустить в «тест», проверить, затем выпустить всем.

### Встроить существующий отдельный плагин

1. Зафиксировать его текущее состояние в git. Всё, что о нём известно (правила, ошибки, непроверенное), перенести в `MODULE.md`.
2. Разделить код: общее заменить сервисами ядра (если в ядре такого ещё нет — сначала добавить в ядро), специфичное перенести в модуль.
3. Переименовать пространства имён и сборку по правилам раздела 3.
4. Сохранить совместимость данных: те же форматы; перенос локальных папок с прежних мест при первом запуске; прежние идентификаторы, от которых зависят сохранённые данные.
5. Убрать у пользователей прежнюю установку (старые манифесты): плагин не должен загрузиться дважды.
6. Проверить в канале «тест» во всех поддерживаемых версиях Revit.

## 5. Ядро

- Изменение ядра касается всех модулей, поэтому после него проверяются все.
- В ядро переносится то, что понадобилось второму модулю. Заранее, «на всякий случай», ничего не добавляется.
- Контракт ядра для модулей меняется с обратной совместимостью — или вместе со всеми модулями в одном выпуске.
- Логики конкретных модулей в ядре нет.
- Различия версий Revit собраны в слое совместимости ядра (раздел 9).

## 6. Работа с Revit API

- Revit API вызывается только в контексте Revit: в команде, событии, простое или через диспетчер ядра. Из потока окон и из фоновых потоков — никогда.
- Обработчики событий Revit быстрые: собрать нужное и отдать работу в очередь ядра.
- Тяжёлая работа идёт порциями в простое Revit, с ограничением времени на порцию: пользователь не должен замечать задержек.
- Вычисления без Revit API (разбор, сравнение, подсчёт) — в фоновых потоках; результат возвращается в поток окна.
- Свои служебные изменения модели (временные виды и т. п.) помечены, и плагин убирает их за собой. Рабочие виды и настройки пользователя не меняются.
- Большие модели — норма: лимиты, порции, виртуализация списков; вся модель в памяти не держится.

## 7. Ошибки и надёжность

- Каждая точка входа из Revit (команда, событие, простой, действие в окне) обёрнута ядром: исключение не уходит в Revit.
- Ошибка пишется в журнал ошибок на компьютере пользователя — с меткой модуля, номером сборки и контекстом. На сервер журнал не отправляется. Окно «О плагине» показывает, где журнал лежит, и открывает его, чтобы пользователь мог переслать файл разработчику.
- Пользователь видит короткое сообщение по-русски: что не получилось и что делать, без технических подробностей. Повторяющаяся ошибка не показывается снова и снова.
- Модуль, упавший при запуске, отключается до следующего запуска Revit, остальные работают. В окне «О плагине» видно, что модуль отключён и почему.
- Модуль можно выключить у всех в общих настройках на сервере, без новой сборки.
- Сайт: ошибка одной страницы или одного действия не останавливает сайт; пишется в журнал ошибок на машине сайта; человек в браузере видит короткое сообщение по-русски.
- Ошибки не глушатся молча. Перехваченная ошибка либо записана в журнал, либо пропущена осознанно — с комментарием, почему это безопасно.

## 8. Данные и совместимость

- Данные бывают трёх видов: общие для команды — на сервере; личные (настройки, вид окон) — на компьютере; кэш — на компьютере, его можно удалить без потерь.
- У каждого модуля свои папки и разделы настроек.
- Форматы файлов, которые читают другие люди и другие версии плагина, меняются только с обратной совместимостью: новые поля добавляются, старые не меняют смысла и не исчезают; чтение терпит незнакомые поля и отсутствие новых.
- Одновременно работают разные версии плагина: у тестовой группы, у тех, кто не перезапускал Revit, в разных версиях Revit. Данные пишутся и читаются так, чтобы все эти версии уживались.
- Папки, ключи и идентификаторы переименовываются и переносятся только вместе со старыми данными (перенос при первом запуске) и с проверкой, что ничего не потеряно: неотправленные данные, кэш, история.
- Запись в общие файлы переживает обрыв сети: сначала во временный файл, затем замена. Если сервер недоступен, данные копятся на компьютере и досылаются позже.
- То, что должно быть одинаковым у всей команды, берётся только из общих настроек компании; личное — из личных.
- **База сайта** — общие данные, которые пишет только сайт. Лежит на локальном диске машины сайта: файл базы в сетевой папке при обрыве связи может испортиться целиком. Копии — автоматически и регулярно на сервер (`Data\<Модуль>`); восстановление из копии проверено заранее, а не в день аварии.
- Устройство базы меняется только переносом данных: перед переносом — копия, после — проверка, что ничего не потеряно. Изменение, после которого старые данные не читаются, недопустимо так же, как для файлов.

## 9. Версии Revit (2023 и 2026)

- Одна кодовая база для всех версий. Каждый проект собирается под обе платформы: .NET Framework 4.8 для Revit 2023 и .NET 8 для Revit 2026. Отдельных копий проекта под каждую версию Revit не делается.
- Различия Revit API и платформ собраны в слое совместимости ядра. Условная компиляция по версии допустима только там; в модуле — в исключительных случаях и с комментарием.
- Используются возможности языка и библиотек, доступные на обеих платформах. Если чего-то нет в .NET Framework, замена делается один раз в ядре, а не обходом в каждом модуле.
- Сторонних библиотек — минимум. В Revit 2023 все плагины делят одно пространство, и разные версии одной библиотеки у разных плагинов конфликтуют. Каждая новая зависимость — решение разработчика.
- Данные одинаковы для всех версий Revit: записанное в 2023 читается в 2026 и наоборот.
- Модуль может работать не во всех версиях Revit. Это записано в `MODULE.md` и в контракте модуля, и ядро не запускает модуль там, где он не поддерживается.
- В Revit проверяется каждая поддерживаемая версия.
- Сайт модуля от версий Revit не зависит: он на .NET 8. Логика, общая с модулем в Revit, собирается и под .NET Framework 4.8, пока модуль работает в Revit 2023. «Минимум библиотек» на сайте мягче (он не в Revit), но каждая библиотека — тоже решение разработчика.

## 10. Выпуск версий и обновление

### Как это устроено

- Каждый выпуск — сборка с номером «год.месяц.день-часыминуты» и коммитом git. Она лежит в отдельной папке на сервере, своей для каждой версии Revit. Выпущенная сборка никогда не меняется: исправление — это новая сборка.
- Указатель канала говорит, какая сборка сейчас у канала. Выпуск — замена указателя одним действием.
- При запуске Revit загрузчик читает указатель своего канала, при необходимости копирует сборку в локальную папку и запускает её оттуда. Файлы на сервере Revit не держит, поэтому выпускать можно в любой момент, даже когда у всех открыт Revit.
- Нет связи с сервером — запускается последняя загруженная сборка. Новая сборка не запустилась — загрузчик возвращается к предыдущей и пишет об этом в журнал.
- Загрузка не задерживает запуск Revit заметно: если скачать не успели, запускается прежняя сборка, а новая подхватится в следующий раз.
- После обновления пользователь один раз видит «Плагин обновлён» и список того, что нового.

### Каналы

- «Тест» — разработчик и выбранные люди, например тот, кто сообщил об ошибке. «Все» — остальные.
- Состав тестовой группы задаётся в общих настройках на сервере.

### Порядок выпуска

1. Исправить, собрать, прогнать тесты. Если тесты не прошли, сборка не выпускается.
2. Записать, что нового, — по-русски, для людей.
3. Зафиксировать изменения в git: сборка помнит коммит.
4. Выпустить в «тест» и попросить проверить (перезапустить Revit).
5. Перевести ту же сборку на «всех», не пересобирая.

Срочное исправление можно выпустить сразу всем, но обычный путь — через «тест».

### Откат и выключение

- Откат — указатель канала переводится на предыдущую сборку.
- Модуль, который мешает работать, выключается в общих настройках, пока готовится исправление.

### Загрузчик

- Меняется редко, отдельным выпуском, с проверкой во всех версиях Revit.

### Сайт

- Обновляется отдельно от плагина, одной командой: собрать, прогнать тесты, сделать копию базы, заменить программу, перезапустить службу. Прежняя версия программы остаётся — откат одной командой.
- Сайт один для всех, а сборки модуля у людей разные (тест, все, не перезапускавшие Revit). Поэтому сайт и мост понимают друг друга в обе стороны: новое добавляется так, чтобы прежние сборки модуля продолжали работать.
- Пользователям — «Что нового» на самом сайте.

## 11. Качество кода

- Код делится на три слоя: логика (без Revit API и окон), связь с Revit, интерфейс. Логику проверяют тесты без Revit, и они запускаются при каждой сборке.
- Исправили «странное» поведение — добавили тест или правило в `MODULE.md`, чтобы оно не вернулось.
- Сборка проходит без ошибок и без новых предупреждений.
- Классы и файлы небольшие, у каждого одна ответственность; имена понятные; повторяющийся код выносится в одно место.
- Пути, имена и префиксы задаются в одном месте (в ядре или в модуле), а не разбросаны строками по коду.
- Комментарии — по-русски и объясняют, зачем и почему, особенно там, где решение неочевидно.
- Производительность — часть правильности: модели в сотни тысяч элементов не должны тормозить Revit.
- Кодировка — UTF-8; окончания строк — по правилам из `CLAUDE.md`.

## 12. Интерфейс

- Одна вкладка «RAS v. 2.0». У модуля свои кнопки, а не своя панель: на какой панели и в каком порядке стоит кнопка, задаёт раскладка ядра, и кнопки разных модулей могут стоять на одной панели. Кнопка, которой нет в раскладке, стоит на панели с названием модуля. У кнопок понятные подписи и подсказки.
- Перенос кнопки на другую панель сбрасывает у пользователей её горячие клавиши и место на панели быстрого доступа: раскладку после выпуска меняют обдуманно.
- Общая тема ядра: светлая или тёмная, как в Revit (там, где Revit это умеет). Цвета — только через общие кисти, без жёстко заданных цветов.
- Иконки кнопок — в едином стиле и с одной палитрой, у каждой — светлый и тёмный вариант; цвет акцента — по отделу модуля. Правила — справочник стиля иконок (`tools\IconBuilder\СТИЛЬ.md`).
- Весь текст — по-русски, коротко, в кавычках-«ёлочках», без англицизмов. Одно понятие называется одинаково во всех модулях.
- Дата и время — «ДД.ММ.ГГГГ ЧЧ:ММ».
- Окна строятся по общим образцам ядра: расположение кнопок, отступы, растягивание.
- Сообщение пользователю отвечает на два вопроса: что случилось и что делать.
- Страницы сайта — по тем же правилам: по-русски, «ёлочки», даты «ДД.ММ.ГГГГ ЧЧ:ММ», одинаковые названия с модулем; светлая и тёмная тема.

## 13. «У меня не работает»: порядок поддержки

1. Узнать, что делал пользователь, в какой модели и какая у него сборка (окно «О плагине»).
2. Попросить прислать журнал ошибок (окно «О плагине» → открыть журнал).
3. Воспроизвести ошибку; если можно — сначала написать тест, который падает.
4. Исправить, прогнать тесты, выпустить в «тест». Если пользователя нет в тестовой группе — добавить.
5. Пользователь перезапускает Revit и проверяет.
6. Перевести сборку на «всех» и записать урок в `MODULE.md`.

Если исправление займёт время, модуль выключают у всех или откатывают сборку.

## 14. Документация

| Документ | Что в нём |
|---|---|
| `PRINCIPLES.md` | этот документ: принципы, общие для всего плагина |
| `CLAUDE.md` | практическое: как собрать, проверить, выпустить; окружение |
| `src\Modules\<Модуль>\MODULE.md` | назначение модуля, устройство, правила модуля, подводные камни, что ещё не проверено в Revit |
| `src\Core\DECISIONS.md` | то же для ядра и загрузчика: решения касаются всех модулей |
| `src\Modules\<Модуль>\DECISIONS.md` | решения по модулю: что решили, почему, что отвергли и почему, состояние (сделано, запланировано, отложено); планы и идеи на будущее |
| `README.md` | для пользователей и BIM-менеджера |
| Что нового (журнал выпусков) | запись к каждому выпуску, по-русски, для людей |

Изменилось поведение — соответствующий документ обновляется в том же изменении.

- **Решения не теряются.** Всё, что обсудили и решили по модулю — в том числе отвергнутые варианты и отложенные идеи, — записывается в `DECISIONS.md` модуля (по ядру — в `src\Core\DECISIONS.md`) в тот же день, с причинами. Решения не удаляются: передумали — новая запись со ссылкой на прежнюю. Перед развитием модуля `DECISIONS.md` читается первым: многое уже обдумано.

## 15. Как ИИ работать с проектом

- Перед работой прочитать этот документ, `CLAUDE.md`, `MODULE.md` и `DECISIONS.md` модуля, с которым предстоит работать; перед изменением ядра — `src\Core\DECISIONS.md`.
- Работать в границах модуля. Ядро и загрузчик менять, только если без этого нельзя, и после этого проверять все модули.
- Не менять форматы общих данных без обратной совместимости. Не переименовывать папки, ключи и идентификаторы без переноса старых данных.
- Не удалять и не перезаписывать данные пользователей и содержимое папки на сервере. Базу сайта не править вручную; устройство базы менять только переносом данных с копией.
- После изменений — собрать под обе версии Revit, прогнать тесты и перечислить, что проверить в Revit: Revit API без Revit не проверить.
- Не выпускать сборку без явной команды разработчика.
- Решение, принятое с разработчиком (и отвергнутые варианты, и идеи на будущее), записать в `DECISIONS.md` модуля с причинами — в том же изменении или сразу после обсуждения.
- Найденный подводный камень записать в `MODULE.md`. Если он общий для всех модулей — предложить разработчику внести его сюда.
- Если есть сомнение, что решение соответствует принципам, — спросить разработчика до того, как писать код.

- Здесь — только принципы, без деталей модулей и команд. Детали — в `MODULE.md` и `CLAUDE.md`.
