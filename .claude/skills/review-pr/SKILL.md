# Проверить запрос на слияние

Работа ведущего разработчика (`LEAD` в `.claude\hooks\guard.py`). Цель — в `main` попадает только то, что собирается под обе версии Revit, проходит проверки и не нарушает принципы. Проверяет Claude, решает человек.

## 1. Что пришло

```
git fetch origin --prune
git branch -r --no-merged origin/main          # ветки, ещё не слитые
git log --format="%h %an %ad %s" --date=short origin/main..origin/<ветка>
git diff --stat origin/main...origin/<ветка>
```
Описание запроса на слияние — попросить человека вставить из GitHub (или открыть, если есть `gh`). Без описания — проверять по коммитам и `DECISIONS.md`.

## 2. Собрать и проверить — в отдельной рабочей папке

Рабочую папку ведущего разработчика не трогать (у него могут быть свои незакоммиченные правки):
```
git worktree add ../RAS_review origin/<ветка>
```
В ней (`out\` — свой, сборки ведущего не задевает):
- `dotnet build tests\RASv2.Tests\RASv2.Tests.csproj -c Release -p:RevitVersion=2023` и `2026`, запуск `out\bin\<год>\tests\RASv2.Tests.exe` — код 0;
- сборка модулей под обе версии: `dotnet build` каждого изменённого `.csproj` с `-p:RevitVersion=2023` и `2026` (не `Release.ps1 -Action build` — он ставит загрузчик и `loader.ini` ведущему);
- `python .claude\skills\finish-change\check_files.py <изменённые файлы>` — из рабочей папки ветки.
- Окно WPF в изменениях — снимок вне Revit (`window_shot.ps1`, навык `new-button`, `Parts` — из папки проверки).
Закончил — `git worktree remove ../RAS_review`.

## 3. Разобрать изменения — по порядку важности

Читать весь `git diff origin/main...origin/<ветка>`, не только заголовки.

**Нельзя сливать, пока не исправлено:**
- не собирается под 2023 или 2026, падают проверки;
- изменения вне модуля без согласования (ядро, загрузчик, `src\Shared`, `tools\`, `setup\`, `Directory.Build.props`, чужой модуль, `PRINCIPLES.md`) — список «можно свободно» — навык `start-task`, «Границы»;
- изменён код модуля или код уже выпущенной кнопки; ломается формат общих данных или настроек без переноса (`PRINCIPLES.md`, раздел 8);
- Revit API вне контекста Revit (фоновый поток, поток окна), окно из события Revit (раздел 6);
- исключение может уйти в Revit: команда или обработчик окна без `try/catch` с журналом и сообщением; вложенный `ShowDialog` без `try/catch`;
- ключ стиля окна совпадает с кистью ядра (`Bg`, `Fg`, `Muted`, `Field`, `Line`, `Row`, `Hover`, `Pressed`, `Accent`, `AccentFg`, `Error`);
- новая сторонняя библиотека без решения ведущего (раздел 9);
- новый модуль не в режиме `только тест` в `{Модули}` `ribbon.txt`;
- секреты, пароли, личные пути (`C:\Users\…`, рабочий стол) в коде.

**Исправить до или сразу после слияния (решает ведущий):**
- зашитые семейства, типоразмеры, параметры, адреса и привычки компании вместо выбора человека или настройки (раздел 6, ред. 10);
- `#if REVIT2023` в модуле вместо `RevitCompat`; `ElementId.IntegerValue` / `.Value` напрямую;
- логика в окне или в команде, а не в `Logic\` с тестами; новое правило без теста;
- цвета в XAML жёстко, а не `{DynamicResource …}`; текст интерфейса не по-русски, без «ёлочек», англицизмы; даты не «ДД.ММ.ГГГГ ЧЧ:ММ»;
- `MODULE.md` / `DECISIONS.md` не обновлены под изменение; решение без причины и автора;
- транзакции без имени по правилам ядра; тяжёлая работа без порций;
- окончания строк, BOM, невидимые знаки (`check_files.py`).

**Заметить, не задерживать:** стиль сообщений коммитов, крупные классы, повторы, комментарии не по-русски.

Каждое замечание — проверить, прежде чем писать: открыть файл, убедиться, что так и есть (не по догадке из названия). Сомнительное — пометить «проверить», а не выдавать за ошибку.

## 4. Отчёт ведущему разработчику

- Вывод одной строкой: **можно сливать** / **можно после правок** / **нельзя** — и почему.
- Что сделано в ветке — 2–4 строки его словами.
- Замечания по группам выше: `файл:строка` — что не так — как исправить.
- Что посмотреть в Revit 2023 и 2026 перед выпуском (из описания запроса и своего чтения).
- Готовый текст для GitHub (ответ автору: спасибо не нужно, по делу; замечания списком с файлами). Отправить в GitHub — сам человек; через `gh` — только если он попросил.

## 5. Слияние — только по его команде

- Через GitHub («Merge pull request») — затем у себя `git fetch origin && git merge --ff-only origin/main`.
- Или локально: `git checkout main && git merge --ff-only origin/main && git merge --no-ff origin/<ветка>`, проверки ещё раз, `git push` — человек.
- После слияния, если менялось видимое людям, — навык `whats-new` к ближайшему выпуску; в «Планах» `CLAUDE.md` — состояние модуля.
