# Перенести функцию из старого плагина

Образец переезда — RAS-Model History (из `D:\Code\SpyPlugin`, ход — «Состояние переезда» в его `MODULE.md`). Свежий пример переноса одной функции — RAS-Sheet Manager, кнопка «Подпись» (из pyRevit «Добавить подписи» и `dwg_clean.py`, 27.10.2026).

**Что и в каком порядке переносить — решает разработчик.** Список кандидатов — `CLAUDE.md`, «Планы» → «Перенос уже написанных функций». Сам не выбирать и не начинать «пока он думает».

## 1. Разобрать, прежде чем писать

1. **Найти актуальную копию.** В `D:\Code\RasPlugin` три копии кода — `RAS`, `RAS_2023`, `RAS_2026` (в `RAS_2023` и `RAS_2026` — `WorkingWithParameters`, `FilterDiagnostics`, `SleevePlacementCommand`, установщики). Сравнить файлы функции во всех трёх (`diff -r`, даты изменения), выбрать самую полную и свежую; расхождения, которые не объяснить, — показать разработчику, а не угадывать.
2. **Зафиксировать состояние источника.** `D:\Code\RasPlugin` — **не git**. С согласия разработчика — снимок (git в той папке или архив в scratchpad) и его номер / путь — в `MODULE.md` нового модуля. Источник не менять и новую работу там не вести.
3. **Выписать всё, что делает функция,** — по коду, а не по названию: команды и окна, какие семейства, типоразмеры, параметры (имена, GUID), фильтры, виды, транзакции, файлы и пути (сеть, `C:\…`, рабочий стол), настройки, зависимости (NuGet, DLL, Excel, AutoCAD), различия 2023 / 2026 (`#if`, отдельные копии).
4. **Найти, что противоречит принципам** (`PRINCIPLES.md`):
   - зашитые семейства, типоразмеры, параметры, адреса и привычки компании → выбор у человека из того, что есть в проекте, или настройка модуля со значением по умолчанию; общие параметры — по GUID из настроек (раздел 6, «Никаких зашитых в коде семейств…»; ред. 10);
   - сторонние библиотеки → каждая — решение разработчика (раздел 9);
   - окна из событий Revit, Revit API из фоновых потоков, тяжёлая работа без порций (раздел 6);
   - глушение ошибок (раздел 7);
   - свои копии общего — журнал, тема, пути (раздел 4, «Чего модулю нельзя»).
5. **Показать разработчику короткий разбор** до кода: что делает функция, какую копию берём и почему, что меняем против оригинала (и что из этого — его решение), в какой модуль ложится (новый или существующий, например «Менеджер листов»), коды кнопок, что ломается у людей при переходе (данные, настройки, горячие клавиши старой вкладки). Ждать «да». Решения сразу — в `DECISIONS.md` модуля.

## 2. Перенести

Шаги раздела 4 `PRINCIPLES.md`:
1. **Модуль.** Новый — по образцу `src\Modules\RAS-Sheet Manager` (проект `RASv2.<Код>.csproj`, `<Код>Module.cs` с `IModule`: `Id` = окончание имени сборки, `Title`, `RevitYears`), `MODULE.md` и `DECISIONS.md` сразу. В `ribbon.txt`, блок `{Модули}` — `<Код> = только тест`, пока не проверено. Существующий модуль — функция в его папку, кнопка — навык `new-button`.
2. **Общее — в ядро, специфичное — в модуль.** То, что уже есть в ядре (журнал `Log`, папки `LocalDataDir` / `UserDataDir` / `SharedDataDir`, тема окон `WindowTheme`, `RevitCompat`, события через `context.Events`), — взять из ядра, свою копию не тащить. Нужно второму модулю, а в ядре нет — предложить разработчику перенести в ядро.
3. **Три слоя:** логика без Revit API (`Logic\`, с тестами в `tests\RASv2.Tests`), связь с Revit, окна. Исходный код обычно всё смешивает — разделять при переносе, а не «потом».
4. **Имена:** пространство имён и сборка `RASv2.<Код>`; транзакции — по правилам ядра; тексты — по-русски, «ёлочки», без англицизмов. Транслит в названиях (`AR_kvartirografiRas`) не переносить.
5. **Одна кодовая база для 2023 и 2026.** Различия копий `RAS_2023` / `RAS_2026` свести к `RevitCompat`; не работает в одной из версий — `RevitYears` без неё, решение собирается под обе (пример — `RASv2.ModelHistory.csproj`).
6. **Данные людей:** форматы прежние или с переносом при первом запуске; прежние идентификаторы, от которых зависят сохранённые данные, — сохранить (раздел 8). Ничего не удалять у людей.
7. **Прежняя кнопка у людей.** Прежний плагин RAS может стоять рядом — его не трогаем (раздел 3, «Прежний плагин RAS»). Записать в `MODULE.md`, что одна функция будет на двух вкладках, пока разработчик не уберёт её из старого.

## 3. Сдать

- Навык `finish-change`: проверки, сборка обеих версий, коммит, список «что посмотреть в Revit 2023 и 2026» — в том числе **сравнение с оригиналом** на одной и той же модели: результат тот же (или отличия — те, о которых договорились).
- `MODULE.md`: откуда перенесено (путь, копия, снимок), что изменено против оригинала и почему, что не проверено в Revit.
- `CLAUDE.md`, «Планы» — функция переехала (ждёт проверки в Revit); из списка кандидатов — убрать, когда выпущено.
- Выпуск — сначала «тест» (`только тест` в `{Модули}` или канал «тест»), всем — по команде разработчика.
