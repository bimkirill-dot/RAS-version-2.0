# Довести изменение до конца

Порядок один и тот же после каждой задачи. Пропущенный шаг потом стоит разработчику времени: несобранная версия Revit, решение, не записанное в `DECISIONS.md`, файл с CRLF, забытый `git push`.

## 1. Проверки и сборка

- **Проверки логики** — под обе платформы:
  ```
  dotnet build tests\RASv2.Tests\RASv2.Tests.csproj -c Release -p:RevitVersion=2023 -nologo -v q
  out\bin\2023\tests\RASv2.Tests.exe
  dotnet build tests\RASv2.Tests\RASv2.Tests.csproj -c Release -p:RevitVersion=2026 -nologo -v q
  out\bin\2026\tests\RASv2.Tests.exe
  ```
  Код возврата 0 — прошли. Новое правило в логике — новый случай в тестах (тесты подключают логику исходниками, `Compile Include` в `RASv2.Tests.csproj`; стиль — как у соседних `*Tests.cs`).
- **Код для Revit** (ядро, модули, загрузчик): `powershell -NoProfile -ExecutionPolicy Bypass -File tools\Release.ps1 -Action build` — обе версии, проверки, сборка разработчику в `out\Releases` (без `pause`, в отличие от `revit.cmd`). Пишет «загрузчик не обновлён» — сказать разработчику закрыть Revit этой версии и повторить; сборок модулей это не касается.
- **Сайт коллизий** — навык `site-check` (браузер на копии базы и установка на его сайт).
- **Navisworks** — `tools\Navisworks.ps1 -Action build`.
- Без ошибок и без **новых** предупреждений (MSB3277 у 2026 — переведено в сообщения, не считается).

## 2. Документы — в том же изменении

- `src\Modules\<модуль>\MODULE.md` — как теперь устроено; найденный подводный камень; что не проверено в Revit.
- `src\Modules\<модуль>\DECISIONS.md` (ядро — `src\Core\DECISIONS.md`) — решение с датой и причинами: слова разработчика в кавычках («разработчик, 30.10.2026: «…»»), отвергнутые варианты и почему, что отложено. Решения не удаляются: передумали — новая запись со ссылкой на прежнюю.
- `CLAUDE.md`, раздел «Планы» — если сдвинулся этап (сделано, ждёт проверки в Revit). Раздел «Выпуск — по шагам» меняется вместе с `Как выпускать.md`.
- `README.md` — если изменилось то, что видят пользователи или BIM-менеджер.
- Подводный камень, общий для всех модулей, — предложить разработчику внести в `PRINCIPLES.md` или «Правила, о которые уже спотыкались» в `CLAUDE.md`, а не вносить молча.

## 3. Файлы

```
python .claude\skills\finish-change\check_files.py
```
Проверяет изменённые и новые файлы: `.cs .csproj .props .xaml .json .md .razor .css .js` — LF; `.cmd .ps1` — CRLF; `.ps1` — с BOM, `.cmd` — без; нет невидимых управляющих знаков. Замечания исправить до коммита.

Правки с обратной косой чертой (`\n`, `\\`, пути Windows) — только Edit или скриптом-файлом через Write. Heredoc в Bash превращает `\\` в `\` и `'\n'` в настоящий перенос строки.

## 4. Коммит

- Только свои файлы: `git add <файлы>`, не `git add -A`. Чужие незакоммиченные правки разработчика (например, `src\Core\ribbon.txt`) не трогать и не включать — спросить, если они нужны в этом коммите.
- Сообщение — одной строкой, по-русски, как в истории (`git log --format=%s -10`):
  `<Модуль>[, область]: «Что» — суть изменения для человека; что исправлено и почему (разработчик: «цитата»)`.
  Примеры: `RAS-Clash Analysis, сайт: «Динамика» — отделы и даты: …`, `Ядро, ribbon.txt: RAS-Model History — «только тест» (разработчик: «…»)`.
- В конце сообщения — строка соавторства из системного напоминания (`Co-Authored-By: …`).
- Сообщение с кавычками и «ёлочками» — через файл: Write в scratchpad, `git commit -F <файл>`.
- После коммита — `git status`. Файл, открытый у разработчика во вкладке VS Code, может быть затёрт старым текстом при сохранении; если это случилось — восстановить из коммита и подсказать «Revert File».
- `git push` делает разработчик сам — не выполнять.

## 5. Память

Обновить заметку «где остановились» (`clash-site-where-we-stopped.md` или свою для модуля): что сделано, что ждёт проверки, открытые вопросы. Решённое и выпущенное — убрать из напоминаний. Не дублировать в памяти то, что уже записано в `DECISIONS.md` и в git.

## 6. Ответ разработчику

- Что сделано — коротко, по пунктам, его словами (без внутренних имён классов, если он их не спрашивал).
- **Что посмотреть в Revit** — отдельным списком для каждой поддерживаемой версии (2023 и 2026): конкретные действия и что должно получиться. Revit API без Revit не проверить — так и сказать.
- Что не сделано или не проверено — честно.
- Напомнить: `git push`; выпуск — только по его команде (`revit.cmd publish test`, «что нового» — навык `whats-new`).
- Без непрошеных предложений «а ещё можно…» в конце, если он не спрашивал о планах.
